## Overview

This release is about where work runs and how much of it there is. **Instance-list queries now sort and paginate in PostgreSQL** before the selected page is hydrated, eligible attribute filters can use **DBA-prepared attribute indexes** declared with `x-indexed` on a `master` schema (generated offline by `wf indexes generate`, never by the runtime), and the existing 1000-character filter-operand limit is finally enforced with an HTTP **400** `filter.valueTooLong` — attribute sorting on ten million rows drops from **3109.5 ms to 4.8 ms** ([#987](https://github.com/burgan-tech/vnext/pull/987)). **`interaction.longPoll` gains a `rule` arm** — a condition script as an alternative to `roles`, fail-closed on both the state signal and the acknowledge endpoint ([#990](https://github.com/burgan-tech/vnext/pull/990)). **`metadata.effectiveStatus` is served** on the instance GET, the list, `GetInstanceTask` and sync responses, and becomes a filter/sort column ([#992](https://github.com/burgan-tech/vnext/pull/992)); an **immutable `Type` column** records how each instance was started — `R` root, `S` SubFlow child, `P` SubProcess child — served as `metadata.type` and filterable as `instanceType` ([#995](https://github.com/burgan-tech/vnext/pull/995)). **Discovery warm-up reads the registry's `domain-list` function** in one call instead of paging raw instances, which needs `vnext-discovery-runtime` **≥ 0.0.7** and raises `L1TtlSeconds` to **600** ([#997](https://github.com/burgan-tech/vnext/pull/997)). **The human-task function is redesigned**: one `UNION ALL` scan per domain instead of one connection per flow, authorization by the leaf state's `queryRoles`, and deny grants that finally veto across the caller's whole role set — 20 concurrent callers on a 45-flow domain used to push 13 of them into `53300 sorry, too many clients already` ([#1016](https://github.com/burgan-tech/vnext/pull/1016)). **Eighteen colliding `WorkflowLogs` EventIds are renumbered** ([#1017](https://github.com/burgan-tech/vnext/pull/1017)). And **five task types now run in-process on Orchestration** — `http`, `daprservice`, `soap`, `statestore`, `cacheaside` — behind a per-type routing seam with the Execution path kept as an opt-in fallback, which also makes `errorBoundary` rules using `errorTypes` match on the remote path for the first time ([#1018](https://github.com/burgan-tech/vnext/pull/1018)). Three fixes complete it: a stranded-Busy chain reserve released on post-commit failure ([#993](https://github.com/burgan-tech/vnext/pull/993)), a DbMigrator DI crash ([#996](https://github.com/burgan-tech/vnext/pull/996)) and an outbox continuation carrier that was never exercised ([#991](https://github.com/burgan-tech/vnext/pull/991)). This release runs on component **schema 0.0.53**.

## Features

### Database pagination, attribute indexes and the filter value limit (#987)

Instance-list queries loaded the entity list and paged in memory; attribute-heavy filters and sorts ran as JSON path expressions over `InstancesData`; and a filter operand longer than 1000 characters could execute as long as the whole filter string stayed under its 5000-character limit.

**Database pagination.** The query now selects `pageSize + 1` identities to learn whether a next page exists, hydrates only the requested page and preserves its order. Equal sort values use `Id` as a stable tie-breaker. The HTTP response shape is unchanged — pagination is still exposed through HATEOAS links. Workflow, schema-role and extension definitions are reused within a page; authorization and extension execution remain per instance. Parameterized SQL construction is shared, comparison semantics are preserved, and EF-managed connections, transactions and command timeouts are used throughout.

**Attribute indexes, owned by the DBA.** `x-indexed: true` on a scalar property opts it into physical preparation as a stored generated column plus an index. Filtering and sorting permissions stay with `x-filterOperators` / `x-sortable`; `x-indexed` only says "prepare a physical projection for this".

```json
{
  "key": "order-master",
  "domain": "sales",
  "flow": "sys-schemas",
  "version": "1.0.0",
  "flowVersion": "1.0.0",
  "tags": ["orders"],
  "attributes": {
    "type": "master",
    "schema": {
      "type": "object",
      "properties": {
        "amount": { "type": "number", "x-indexed": true, "x-filterOperators": ["gt"] }
      }
    }
  }
}
```

- **The master marker is `attributes.type == "master"`, exactly.** The value is free text — the enum is removed, legacy and custom types stay valid — but only that exact string permits `x-indexed` metadata and contributes index SQL. Missing, null, blank or any other value never means master. There is no separate component-root `type` field.
- **`x-indexed` anywhere in a non-master schema is rejected at publish, even `x-indexed: false`.** It is allowed only on scalar `string` / `number` / `integer` / `boolean` properties under fixed object property paths; arrays, objects, `$ref` and conditional schemas are rejected. Date fields use `format: "date-time"`.
- **The runtime never runs index DDL.** Publishing a Master schema or workflow schedules no index work; reading instances prepares nothing. The `vnext-workflow-cli` (1.0.14+) generates the SQL offline:

  ```bash
  wf indexes generate --flow money-transfer --output ./index-sql
  ```

  Each invocation writes a new batch folder with one `.sql` per workflow, a `manifest.json` (source versions, SHA-256 checksums, physical index definitions) and DBA execution notes. The command reads only local files — no API, no database, no hook into `sync` / `update`. The DBA reviews and executes each file in a maintenance window (`psql -X -v ON_ERROR_STOP=1 …`): the script takes a per-flow advisory lock and an **ACCESS EXCLUSIVE** lock on `InstancesData` (5 s lock timeout, editable during review), validates conversions across current *and* historical data, adds the missing stored generated columns (`q_<hash>`) in one `ALTER TABLE`, reuses structurally equivalent existing indexes, builds trigram GIN indexes for `contains` / `like` / `startswith` / `endswith`, records the selected index names in `AttributeIndexCatalog` and commits atomically. This is not `CREATE INDEX CONCURRENTLY` — plan disk, WAL, replicas and duration for column rewrites on large tables. `--retire-obsolete` removes obsolete owned projections after a type change.
- **Runtime activation is a config switch, and it fails safe.** `AttributeIndexes:Enabled` (default `false`) routes eligible filters, sorts and aggregations to ready projections; `DisabledFlows` rolls a single workflow back. The ready catalog is read through the distributed cache (`CatalogCacheSeconds`, 30) with a refresh lock coalescing misses across replicas. Missing or unready projections, catalog connection/read failures, cache failures and refresh-lock failures **all fall back to the JSON expression** and log `AttributeIndexCatalogFallback` (warning, EventId **70021**) without caching the failure as an empty snapshot, so a later request recovers immediately.

**The filter value limit is enforced.** A filter operand longer than **1000** UTF-16 code units (decoded `.NET string.Length`, inclusive) now returns **HTTP 400** with `filter.valueTooLong` before any SQL executes. It applies to instance columns and JSON attributes, including nested and logical conditions and filters inside request envelopes; `in` / `nin` elements and `between` endpoints are checked individually, including legacy comma-separated operands. Stored instance data is untouched and values are never truncated; the 5000-character filter-string limit and the `includes` payload limits stay in place. `GetInstancesTask` validates both local and remote calls, so a rejected operand **fails the task and can trigger the workflow error boundary**.

p95 latency on ten million current-version rows (P = without indexes, I = with; concurrency C=1 / 10 / 50; `×N` is an error count):

| Query | P10 | I10 |
|---|---|---|
| `attribute-sort` | 3109.5 / ×50 / ×100 | **4.8** / 26.2 / 75.5 |
| `min-all` | 1796.7 / ×49 / ×100 | **1.9** / 4.5 / 16.6 |
| `max-all` | 1413.4 / ×50 / ×100 | **2.2** / 2.4 / 14.1 |
| `startswith` | 3824.4 / ×50 / ×100 | 17.7 / 25.9 / 122.6 |
| `gt` / `between` / `in` | ×10 / ×50 / ×100 | 8–11 / 19–48 / 72–101 |
| `count-all` | ×10 / ×50 / ×100 | 374.8 / 769.4 / 3729.5 |

Read the table honestly: several range and text queries report errors without indexes and measured latencies with them, so those cells support no speedup ratio; some simple `eq` / `ne` queries are marginally slower with indexes; `deep-page` errors in every profile, and `sum` / `avg` / `group-low` still error at C=50 with indexes. This delivery changes maintenance ownership — it does not claim a new general query-performance benchmark.

### Rule-based long-poll interaction authorization (#990)

A state's `interaction.longPoll` could gate the interaction only with `roles`. It can now carry a **condition rule** instead — the same `IConditionMapping` script contract view and notification rules use, compiled and cached by the shared script engine:

```json
"interaction": {
  "longPoll": {
    "terminate": true,
    "rule": { "location": "./InteractionGate.csx", "code": "<base64>" }
  }
}
```

- **One arm or the other, never both.** `WorkflowValidator` rejects a `longPoll` declaring both `roles` and `rule`, validates the rule's script body like every compilable slot, and validates the `roles` grants' dynamic-role syntax. There is one rule per interaction — no list, no fallback entry.
- **Both surfaces, one gate.** The state function's signal emit and the acknowledge endpoint admit through the same `LongPollInteractionGate`, which owns the whole arm selection (rule, else roles, else allow) so their verdicts cannot diverge. Caller roles are resolved lazily, only when the roles arm applies.
- **Fail-closed.** A rule returning `false`, throwing or failing to compile denies: the signal is not emitted and the acknowledge answers **403**. A broken rule cannot strand the instance — the fallback-timeout job resumes the pipeline regardless of callers.
- The rule's context carries the workflow, the instance, request headers and query parameters (the acknowledge endpoint forwards headers only). Read instance data through `context.Instance.Data`, materialized lazily. **`context.Body` is deliberately not populated** — this surface has no request payload, and pre-filling it cost a full serialize + parse on every poll even for header-only rules. A view rule reused here must switch `context.Body.*` reads to `context.Instance.Data.*`, or it throws and denies.
- **Caching posture.** A rule's inputs are not part of `CallerScopeHash`, so a state body whose interaction is rule-gated is never stored in the shared body cache (the same applies to a bubbled subflow interaction whose gating arm the parent cannot see). The fingerprint 304 fast path is unchanged, which leaves one accepted gap: a caller whose rule inputs change while the fingerprint does not can keep receiving 304 with the previous verdict until the next state/status change. Enforcement is never stale — the acknowledge evaluates the rule fresh on every request.

> **Reference:** PR [#990](https://github.com/burgan-tech/vnext/pull/990) — see also [Workflow](/docs/components/workflow) and [Built-in Functions → State](/docs/components/functions/built-in).

### `effectiveStatus` served on the instance projection (#992)

`metadata` carried `effectiveState` but no status counterpart, so `metadata.status` was the instance's **own** row status. A parent is `Busy` for its child SubFlow's entire lifetime by design, so that field could not tell a child waiting on a human task from real work — while the state function, polling the same instance, reported the deepest active SubFlow's status. Two surfaces, two answers. v0.0.93 added `Instance.EffectiveStatus` as fingerprint material and explicitly left serving it as a separate decision; **this is that promotion.**

| Surface | How |
|---|---|
| `GET …/instances/{instance}` · `GET …/instances` (list) · `GetInstanceTask` (type 19) | `metadata.effectiveStatus` — one `InstanceMetadataDto` constructor feeds all three |
| sync `start` / `transition` responses | `effectiveStatus` on `InstanceOutputBase` (an async `202` does not carry it) |
| instance queries | `effectiveStatus` filter/sort column, by name or code (`Active` / `A`) |
| rule and role-grant script contexts | `ExpressoInstanceView.EffectiveStatus`, `$.context.Instance.EffectiveStatus` |

`metadata.status` is unchanged — the change is purely additive. Responses read a new accessor, never the raw column:

```csharp
Status.IsTerminal || EffectiveStatus.IsTerminal ? Status : EffectiveStatus
```

The propagated projection is served only while neither side is terminal, and both arms reproduce what the state function already answers. A terminal projection at a running level is the SubFlow completion window — the child published `C`/`F` upward at its rest point while this level's correlation is still open and it is resuming; the state function's `subFlowIsTerminal` guard answers `Busy`, and the clamp matches it. A terminal own status with a stale non-terminal projection is a cancel or fault cascade, which the write side cannot repair: the cascade completes the level while the child's correlation is still open, and cleanup closes it afterwards with nothing left to restamp the column. **Found by running it**: cancelled parents served `effectiveStatus: "A"` against the state function's `"C"` — 15 rows in a local database. Do not "simplify" the clamp to `HasActiveSubFlow ? projection : own`: the list query does not load child correlations, so that predicate is `false` for every list item.

Two projection-hygiene fixes come with it: `Instance.CreateSnapshot()` now carries `EffectiveStatus` (the script context's instance *is* a snapshot, so every script and role grant used to read the constructor's `Active` default), and the SubFlow terminal paths resync the status projection alongside the `EffectiveState` reset they already did. The state function **body is untouched** — no new field, `ResponseShapeVersion` stays **v9**, and the terminal-path resync shares the same `UpdateAsync` as the correlation completion that was already invalidating the ETag, so no new long-poller wake-up is introduced. `InstanceStatus.IsTerminal` becomes the single definition of "terminal"; `EffectiveStatusDrift` (20445) turns from a measurement into a regression sentinel.

:::note
**Filters see the stored column, not the clamp** — they run in SQL. `filter={"effectiveStatus":{"eq":"Completed"}}` can match a parent whose served `effectiveStatus` reads `Busy`. For "is this flow done?", filter on `status`.
:::

Verified against a local runtime with the `subflow-orchestration` flow: 205 dense samples through a normal completion cascade and 147 through a cancel cascade with an Active child — `metadata.effectiveStatus` equalled the state function's `status` in **every** sample, 0 terminal leaks, 0 `EffectiveStatusDrift` events, and the 15 previously divergent rows now serve `C`/`C`.

> **Reference:** PR [#992](https://github.com/burgan-tech/vnext/pull/992) — see also [Instance filtering](/docs/how-to/instance-filtering) and [GetInstance task](/docs/components/tasks/get-instance).

### Immutable instance `Type` — root, SubFlow child, SubProcess child (#995)

An instance carried no record of its own origin. The only signal was the `parent.*` block inside `ExtraProperties` — a `text` column holding JSON, unusable for filtering, sorting or grouping without a `::jsonb` cast, and served on no read surface. Reporting could not ask "was this a root, a SubFlow child or a SubProcess child?" of a finished instance at all. It was also **not a correct discriminator**: `SetInfoMetadata` copies the instance's *own* workflow type code into `parent.flowtype` when the key is absent, so a workflow whose definition declares `type: "S"` and is started directly through the API carries `parent.flowtype: "S"` with no parent — and `IsSubFlow` answers true for it.

`Instances."Type"` — `R` root, `S` SubFlow child, `P` SubProcess child — is derived once at creation and never updated:

```text
non-empty parent.id  →  parent.flowtype == "S" ? S : "P" ? P : R
otherwise            →  R
```

- Served as **`metadata.type`** on the instance GET, the list and `GetInstanceTask` (one constructor feeds all three); `RoleGrantEvaluator` emits the bare code (`"S"`). Not on the state function body and not on sync responses, so `ResponseShapeVersion` stays v9 — an immutable column cannot invalidate a cached response.
- Filterable and sortable as **`instanceType`**, by name or code (`Root|R`, `SubFlow|S`, `SubProcess|P`), on both filter engines. **Why not `type`:** instance columns and data attributes share one namespace on the legacy and GraphQL filter surfaces and are told apart purely by name, so claiming `type` would silently retarget the existing filters of every domain whose schema has a business field called `type`. Verified live: `type=eq:S` returns 0 against ten `S` rows while `instanceType=eq:S` returns 10.
- **Purely additive.** `IsSubFlow` / `IsSubItem` and every `parent.*` reader are untouched, mislabel included; the `parent.*` contracts remain the source of truth for the relationship itself. `Type` records the start origin, not a live link. Three locks keep it immutable: latched on `IsTransient`, carried through `CreateSnapshot`, and pinned `IsModified = false` in the repository's `UpdateAsync`.

Migration `20260916140000_AddInstanceType` adds the column with `NOT NULL DEFAULT 'R'` (catalog-only on PostgreSQL 11+, no rewrite) and backfills only child rows from the `parent.*` block. Measured against 44 schemas: **11,638 rows → R=6877, S=4050, P=711**, matching the pre-migration projection exactly with 0 misclassifications. On a very large `Instances` table raise `SchemaMigration:CommandTimeoutSeconds` (default 600) and `LockExpirySeconds` above it before deploying.

Two things found by running it rather than reading it: every `instanceType` filter returned **500** in the first version, because the GraphQL path re-validated an already-resolved column name against the user-facing whitelist — fixed with a separate `IsResolvedInstanceColumn` and three regression tests; and a hand-written migration without `[DbContext]` / `[Migration]` attributes is never discovered by EF **while the migrator still reports success**.

> **Reference:** PR [#995](https://github.com/burgan-tech/vnext/pull/995) — see also [Instance filtering](/docs/how-to/instance-filtering) and [Workflow](/docs/components/workflow).

### Discovery warm-up from the registry's `domain-list` function (#997)

The discovery cache's bulk warm-up paged the registry's raw domain instance list and re-derived the projection client-side — a server-side filter with a 4xx-retry-unfiltered dance, an authoritative client-side `metadata.status` check, a `domainName` → `key` fallback, `links.next` avoidance, repeated-page stall detection and a 20-page cap. About 180 lines, all deleted.

`ListAllAsync` is now one `GET {BaseUrl}/{Domain}/functions/domain-list`, parsing `{ "items": [ { domainName, baseUrl, appId, healthUrl } ] }`. The registry owns the filtering, ordering and name resolution, and caches the answer itself for 24 h with write-through eviction on the `domain` workflow's `start-domain` and `update` transitions — so a refresh window usually costs it a cache read, not an instance query. The read keeps its `Result` contract, its all-or-nothing failure policy and its own named `HttpClient` (`ServiceDiscoveryBulk`), because a failing bulk read must not trip the circuit breaker guarding the per-domain lookup the cache falls back to.

```json
{
  "ServiceDiscovery": {
    "Cache": {
      "Enabled": true,
      "L1Enabled": true,
      "L1TtlSeconds": 600,
      "TickIntervalSeconds": 60,
      "RefreshIntervalSeconds": 3600,
      "L2TtlSeconds": 7200,
      "WarmupLockLeaseSeconds": 30,
      "DomainListEndpointTemplate": "/{0}/functions/domain-list",
      "DomainListExpectedMax": 500
    }
  }
}
```

- **Removed:** `BulkPageSize`, `MaxPages`, `BulkEndpointTemplate`, `BulkFilter`, `AcceptedStatuses`. Unbound keys left in a deployed `appsettings.json` are ignored, so removal cannot fail a startup — they simply no longer do anything. **Added:** `DomainListEndpointTemplate` (`{0}` = the registry domain; configurable for a gateway path variation) and `DomainListExpectedMax` (500, the registry function's own page size).
- **No fallback to the paged read — an explicit decision.** A registry whose package predates `domain-list` answers 404, every window fails with `DomainListEndpointMissing` (EventId **50039**), and the cache stays cold: lookups keep resolving live, which is the behaviour with the cache switched off. Upgrading against an older registry is not an outage, but the cache never warms.
- **The registry function serves a single page** and signals nothing when it truncates. Reaching `DomainListExpectedMax` is logged at Warning (`DomainListCeilingReached`, **50038**) and the list is published anyway — the domains it holds are still served from cache, and the ones beyond the ceiling merely pay a live lookup. Raising the ceiling is a change on the registry side.
- **`L1TtlSeconds` 60 → 600 changes an operational property.** L1 is the one layer the refresher cannot overwrite on other pods, so this is how long a forced `POST utilities/discovery/refresh` takes to reach the fleet: up to ten minutes rather than one. Worst-case staleness after a domain moves goes from ~61 to ~70 minutes. Set it back to 60 to keep the previous behaviour; it must stay below `RefreshIntervalSeconds`.

Untouched on purpose: the refresh hosted service and refresher (lock, marker, lease, empty-is-a-failed-window), the caching client (keys, TTLs, single-flight), both discovery providers, and `POST utilities/discovery/refresh`. Verified in the cross-domain lab against `@burgan-tech/vnext-discovery-runtime@0.0.7`: the outbound request is exactly `GET …/discovery/functions/domain-list` with no `page=` / `filter=`, 11 domains warmed, and killing the registry made the refresh answer `Failed` while leaving every entry in place.

> **Reference:** PR [#997](https://github.com/burgan-tech/vnext/pull/997) — see also [Service discovery configuration](/docs/configuration/service-discovery).

### Human-task function: one scan per domain, authorized by the leaf state's `queryRoles` (#1016)

`GET /api/v1/{domain}/functions/human-task` answers "which human tasks is this caller expected to act on?" — morph-idm calls it once per registered domain and merges the answers. Two things about it turned out to be one: what the list is **selected** by, and what it is **authorized** by.

**Selection was one connection per published flow, on every request.** Every flow of a domain lives in a schema of the same database, so the per-flow scans differed only in the `FROM` clause — yet each ran as its own parallel branch with its own unit of work and pooled connection, whether or not the flow had any work. Measured on a 45-flow domain against PostgreSQL's default `max_connections = 100`, with N concurrent *distinct* callers (the cache is keyed per caller, so N callers are N rebuilds by construction):

| Concurrent callers | Before | After |
|---:|---|---|
| 10 | all 200 | all 200 |
| 20 | **13 of 20 → 500** (`53300 sorry, too many clients already`) | all 200 |
| 40 | **16 of 40 → 500** | all 200, peak 51 connections |
| 80 | — | all 200, peak 54 connections |

The scan is now **one `UNION ALL` statement on one connection** — one parenthesised arm per flow, batched at `FlowsPerScanStatement` arms per statement, each arm planned independently so every one stays on the new partial index `IX_Instances_HumanTaskV2` (`CreatedAt DESC, Id` with `Key` included). The predicate — `Type IN ('R','P') AND Status IN ('A','B') AND EffectiveStatus = 'A' AND EffectiveStateSubType = 6` — lives in exactly one constant shared by the query, the EF index filter and the migration, because PostgreSQL proves partial-index applicability over the predicate's parse tree and a re-spelling silently costs the index. `'P'` is included because a SubProcess is fire-and-forget and its human states used to be invisible; `'S'` stays excluded because its state is projected onto the root that represents it. `EXPLAIN (ANALYZE)` over all 44 arms of the lab domain: `Index Only Scan`, `Heap Fetches: 0`, **0.92 ms execution** against 26 ms of planning — one round trip instead of 44. The descent keeps the fan-out, because that is the phase that walks into other flows and other domains; it now runs only over flows *with* candidates (3 of 47 in the lab trace).

**Authorization is the leaf state's `queryRoles`.** The list is a *visibility* question — which button a caller is offered is settled later by the state function — so the gate is the same one the state, data, view, schema and incident reads use, resolved as the parent's stamped state override, then the leaf state's own `queryRoles`, then the workflow's root `queryRoles`. It used to authorize by an OR over the state's available transitions, which made the list a fourth authorization surface that skipped the `availableIn` narrowing the state function applies, and made a role-less `cancel` — appended from every state — a back door authorizing every caller for every instance. **A leaf whose state and workflow both declare no `queryRoles` is dropped**, logged as `HumanTaskQueryRolesUndeclared` (**20459**) with instance, flow, state and domain: a task list is the one read surface where "no rule authored" must not mean "everyone".

**Deny grants now veto across the whole role set.** `RoleGrantEvaluator` evaluated grants per caller role inside a loop that returned on the first allowed role, so a deny for role B was never reached once role A had matched an allow — a caller holding `[approver, blocked]` passed. The deny group now runs **first, as an AND** over every role the caller carries (one breach refuses outright), and the allow group runs second as an OR. This is more restrictive, and it applies to the state function too, which shares the evaluator.

The cross-domain descent is batched by level and grouped by `(domain, flow)`: a cross-domain group is one `POST …/{domain}/workflows/{workflow}/internal/human-task-leaf/batch` call, and the far side runs the same resolver and answers finished — one call per domain boundary, not per instance per level. A SubProcess is addressed by its own `Id`, since `SubflowStarter` copies the parent's `Key` onto the child. Cache hits answer in **2–9 ms** without touching a database; a cold rebuild is **27–63 ms**.

```json
{
  "HumanTaskFunction": {
    "PerSchemaLimit": 200,
    "ResultCap": 500,
    "MaxDescentDepth": 10,
    "FlowsPerScanStatement": 64,
    "FanoutParallelism": 10,
    "MaxConcurrentDescents": 32
  },
  "HumanTaskFunctionCache": {
    "Enabled": true,
    "TtlSeconds": 60,
    "AllowClientOverride": true
  }
}
```

- `PerSchemaLimit` is enforced in SQL and `ResultCap` after authorization and ordering; both bound the sort and the response, not the scan. Truncation is signalled by the **`X-VNext-HumanTask-Truncated`** response header, because the body is a bare JSON array morph-idm deserializes as a list. `FanoutParallelism` bounds descent branches within one request; `MaxConcurrentDescents` bounds their product across all in-flight requests — keep it above the first and below the connection pool.
- The response cache is a plain TTL cache keyed by domain, caller scope and a hash of every non-volatile header; **`X-VNext-Cache-Override`** skips the read but never the write, behind the same single-flight gate as an ordinary miss, and is honoured only while `AllowClientOverride` is true.
- Three spans on the existing `BBT.Workflow.Instances.Read` source — `HumanTask.Scan/{domain}`, `HumanTask.Descend/{flow}`, `HumanTask.Authorize/{flow}` — with counters (`vnext.humantask.schemas_scanned`, `.candidates`, `.returned`, `.dropped`, `.workflows_dropped`, `.truncated`) on the `Instance.Read/humanTasks` envelope. Drops are logged per reason under **20450–20457**.

:::warning
**The index swap closes the rollback window.** Migration `AddHumanTaskOwnColumnsIndex` creates `IX_Instances_HumanTaskV2`; `DropLegacyHumanTaskIndex` then drops `IX_Instances_HumanTask`. While the old index existed, reverting the predicate still landed on an indexed plan; after the drop a revert falls back to a sequential scan per flow schema. It was dropped because a partial index evaluates its predicate on every write, and the old one cast `text→jsonb` per tuple for six `INCLUDE` columns no read used. `CREATE INDEX CONCURRENTLY` is unavailable inside a migration transaction, so each build takes a `SHARE` lock once per flow schema — measure schema count and row counts first.
:::

> **Reference:** PR [#1016](https://github.com/burgan-tech/vnext/pull/1016) — see also [Built-in Functions](/docs/components/functions/built-in) and [Authorization](/docs/concepts/authorization).

### `WorkflowLogs` EventIds renumbered (#1017)

`WorkflowLogs.cs` had **18 EventIds each declared on two unrelated `[LoggerMessage]` methods**. An EventId is what an operator filters on; two unrelated messages sharing one means a dashboard or alert keyed to that number silently matches both — `TimeoutMappingFallback` and `InstanceFaultedCleanupHookProcessing` both answered to `40100`. Nothing catches this: the source generator accepts a duplicate and the collision exists only in the log pipeline. (`40075` is *not* one of them — `JobFailed` is two overloads of the same event, one taking an exception and one a Result error string, and stays shared by design.)

Which side moved was decided by region footprint: each collision is a stray poking into a block another region holds contiguously, so the stray moves and new ids are taken above the region's own block, never filling a gap that a saved query might still name.

| Moved | From → to |
|---|---|

### Task invocation routing: five types run in-process on Orchestration (#1018)

Every task with a prepared binding was shipped as a `TaskEnvelope` to the Execution service over Dapr service invocation. **Five wire task types now run in-process on Orchestration by default** — `http` (6), `daprservice` (3), `soap` (16), `statestore` (17), `cacheaside` (18) — behind a routing seam: `ITaskInvocationRouter` decides, `ITaskInvocationDispatcher` acts, `ILocalTaskInvoker` implementations do the work. The invocation cores are extracted into a new `BBT.Workflow.Execution.Core` project so Orchestration and Execution share one implementation. The Execution path is **kept alive as an opt-in fallback, per type**, so any type can be reverted with one config key and no code change.

```json
"Workflow": {
  "TaskInvocation": {
    "DefaultMode": "Remote",
    "Modes": {
      "http": "Local",
      "daprservice": "Local",
      "soap": "Local",
      "statestore": "Local",
      "cacheaside": "Local"
    }
  }
}
```

- **Resolution order**, first match wins: a per-task override (`config.executionMode` — a seam for a future schema release, always `null` today) → `Workflow:TaskInvocation:Modes:{wireType}` (case-insensitive) → `DefaultMode` → the **capability gate**: a type resolved to `Local` with no registered local invoker degrades to `Remote` instead of failing. A configuration mistake is a silent fallback to the previous behaviour, not an outage. Every other wire type (`daprbinding`, `daprhttpendpoint`, `daprpubsub`, `daprconversation`, `python`, trigger and query types) has no local invoker and always resolves to `Remote`.
- `DefaultMode` ships as `Remote` so a task type added tomorrow does not start performing egress from the orchestrator just by existing. `ExecutionMode.Custom` is **rejected at startup** for both `DefaultMode` and every `Modes` entry — it exists in the enum for a plugin story that was never built and would otherwise behave as an inert `Remote`.
- **`Workflow:TaskInvocation:MaxConnectionsPerServer`** (code default **50**, previously hardcoded **10**) caps the per-target connections of the named HTTP clients shared by every in-process `http` / `soap` task and the deprecated type-22 task. It applies only to Orchestration's own clients; the Execution host's stay hardcoded at 10, so reverting a hot single-target type back to `Remote` under load also drops that ceiling.
- **`Workflow:TaskInvocation:LocalInvocationTimeoutSeconds`** (code default **60**) is the local-path counterpart of `ExecutionApi:InvocationTimeoutSeconds`. It matters most for `daprservice`, `statestore` and `cacheaside`, whose bindings have no `timeoutSeconds` field at all — without this dial a locally-run task of those types had no deadline below the 300 s job budget.
- **Options bind once at startup.** Changing a mode requires an Orchestration restart; editing the ConfigMap alone changes nothing in a running pod. Confirm the new pods picked it up from the `vnext.task.invocation.mode` span tag, which every `Task.Invoke` now carries. No Execution redeploy is needed either way.
- **The function response cache travels the same seam** — `StateStoreCacheGateway` now takes `ITaskInvocationDispatcher`, because it is a `statestore` invocation like any other.

**What the local path loses:** no Dapr sidecar circuit breaker between the orchestrator and a slow downstream, and the `statestore` / `cacheaside` / function-cache traffic now shares the orchestrator sidecar's Dapr state component and go-redis pool with the platform's own caches. There is no cap on the state path — a noisy domain `statestore` task can, in principle, starve the platform cache reads on the same pool; cache-heavy domains should raise the orchestrator's Redis `poolSize` in Helm. A bulkhead for the state path is a tracked follow-up.

**Measured**, `Task.Invoke` p50, same hosts and components, only `Modes:*` differing:

| Wire type | Local | Remote | Δ |
|---|---:|---:|---:|
| `http` | 5.87 ms | 8.29 ms | +2.42 ms |
| `soap` | 6.46 ms | 8.34 ms | +1.88 ms |
| `statestore` | 0.69 ms | 2.24 ms | +1.55 ms |
| `cacheaside` | 0.70 ms | 2.40 ms | +1.70 ms |

Function response cache `Cache.Get` on a hit: 0.68 ms local against 2.19 ms remote. **This is not a transition-level speedup:** at one task per transition, 1.5–2.4 ms sits inside the run-to-run variance of a 30–50 ms transition; the saving multiplies with task count. Trace integrity was verified first across 318 transition traces — no required span family missing in either mode.

:::warning
**Orchestration now needs the Dapr `state` component.** Local `statestore` / `cacheaside` resolve their store through `DAPR_STATE_STORE_NAME` in whichever host runs the task — now the orchestrator. Local dev, docker and the Helm chart already supply it. What can break silently is a **custom `storeName`** on a `StateStoreTask`, `CacheAsideTask` or function `cache` block: a component scoped only to the execution app id resolved fine under `Remote` and fails at first execution under the new `Local` default, with no publish-time or startup signal. Rescope it to the orchestrator, or set `"statestore": "Remote"` and `"cacheaside": "Remote"` until you can.
:::

**Type 22 External HTTP is deprecated.** It existed so a user-defined URL call could run inside the Orchestrator instead of being shipped to Execution; type 6 now does that under the shipped configuration through the same send core, with a per-type `Remote` fallback that type 22 never had. Existing definitions keep working unchanged; new definitions should use type 6.

**A behaviour change on the *remote* path, found on the way.** The invocation cores write `"ExceptionType"` in PascalCase; the remote JSON round trip camel-cased dictionary keys; `ErrorNormalizer` looked the key up ordinally. So **`errorBoundary.onError` rules using `errorTypes` have silently never matched on the remote path.** Metadata and header lookups are now case-insensitive at both seams (`InvocationKeyNormalizer`), so the invocation mode is not observable through a lookup — and domains with dormant `errorTypes` rules will see boundary handlers fire that never fired before.

> **Reference:** PR [#1018](https://github.com/burgan-tech/vnext/pull/1018) — see also [Task invocation configuration](/docs/configuration/task-invocation), [HTTP task](/docs/components/tasks/http), [State Store task](/docs/components/tasks/state-store) and [Cache-Aside task](/docs/components/tasks/cache-aside).

## Behavior Changes

Eight items change observable behaviour, and most need a definition- or deployment-side audit before upgrading. A filter operand longer than **1000** characters now returns **400** `filter.valueTooLong` instead of executing, and a `GetInstancesTask` carrying one fails and may trigger the error boundary ([#987](https://github.com/burgan-tech/vnext/pull/987)); `x-indexed` is rejected at publish on any schema whose `attributes.type` is not exactly `master`, `false` included ([#987](https://github.com/burgan-tech/vnext/pull/987)). The human-task list is authorized by the leaf state's `queryRoles` and drops undeclared states, deny grants veto across the caller's whole role set, and the index swap closes the rollback window ([#1016](https://github.com/burgan-tech/vnext/pull/1016)). `errorBoundary` rules using `errorTypes` now match on the remote path too ([#1018](https://github.com/burgan-tech/vnext/pull/1018)); Orchestration needs the Dapr `state` component and a custom `storeName` must be scoped to it; type 22 is deprecated. Eighteen `WorkflowLogs` EventIds moved ([#1017](https://github.com/burgan-tech/vnext/pull/1017)). Discovery drops five bulk keys, requires `vnext-discovery-runtime` ≥ 0.0.7 and raises `L1TtlSeconds` to 600 ([#997](https://github.com/burgan-tech/vnext/pull/997)). Each item, its impact direction and the migration steps are documented in the [v0.0.94 breaking changes announcement](/blog/breaking-changes/breaking-changes-v0-0-94).

## Fixes

- **A failed post-commit forward no longer strands the whole chain Busy** ([#993](https://github.com/burgan-tech/vnext/pull/993)). An async transition accepted on a parent holding an active SubFlow marks the chain Busy down to the leaf *before* answering 202 — required, since the client only observes the leaf. When the post-commit forward then failed with a client error, the failure policy declined to fault the instance, and that exit ran neither `Settle` nor `Fault`. Every level stayed Busy permanently: Busy has no recovery API and no incident is raised. **Measured in production: 51 stranded instances in 30 days.** `ReleaseSubflowChainAsync` — written, documented and tested — had zero call sites. `TransitionRunner` now compensates on that one exit, gated on the reserve the accept actually took (`SubflowChainReserved`, not `IsPreReserved`), through an identity-only overload because the stage scope is already disposed, and deliberately **not** on the fault path, where `Instance.Fault` already cascades downward. The release flips the leaf `Busy → Active` via CAS and returns each ancestor's `EffectiveStatus` projection to `Active`, which moves the state-function ETag and wakes the long-poller.
- **DbMigrator starts again** ([#996](https://github.com/burgan-tech/vnext/pull/996)). #987 registered the attribute index catalog in the core infrastructure module shared by every host; its implementation needs `IDistributedCacheService`, which the DbMigrator — a minimal host with no distributed cache — does not have, so `ValidateOnBuild` crashed at startup. The registration moves to `AddInfrastructureRuntimeServices`, called only by hosts that also register the cache. A generic test now asserts that nothing the core module registers takes `IDistributedCacheService`.
- **The outbox continuation carrier is exercised, and the two tracing defects it hid are fixed** ([#991](https://github.com/burgan-tech/vnext/pull/991)) — `ActivationActivity` and the instance controller's enqueue relay now have tests driving the carrier end to end; the span-tree document is updated accordingly.
- **Every `instanceType` filter returned 500** in the first build of #995 — the GraphQL path re-validated an already-resolved column name against the user-facing whitelist; fixed before release with a separate resolved-name check ([#995](https://github.com/burgan-tech/vnext/pull/995)).
- **`Instance.CreateSnapshot()` carries `EffectiveStatus`** — every script and role grant used to read the constructor's `Active` default ([#992](https://github.com/burgan-tech/vnext/pull/992)).
- **`EffectiveStateSubType` is reset when a SubFlow completes** — it had no reset writer at all, so a finished child's `Human` sub-type stuck to its parent permanently and that parent was listed as an open human task for every caller. `Complete` and `Cancel` also repair the raw `EffectiveStatus` column at the source ([#1016](https://github.com/burgan-tech/vnext/pull/1016)).
- **The parent's stamped state-role override finally has a reader** — `SubflowStarter` had always written `subflow.state_role_overrides` onto the child and nothing read it; both override readers also deserialized with case-sensitive options, so `Role` came back null and every override silently fell back ([#1016](https://github.com/burgan-tech/vnext/pull/1016)).
- **A boot-time DI cycle** (`HttpTaskExecutor → … → LocalCacheAsideTaskInvoker → ILocalTaskInvokerRegistry`) that stopped every host from starting survived 21 commits because every unit test hand-constructed its invoker; a container-building registration test now guards it ([#1018](https://github.com/burgan-tech/vnext/pull/1018)).

## Summary

- **List queries page in the database**; `x-indexed` on `attributes.type: "master"` schemas declares DBA-prepared projections generated by `wf indexes generate`; `AttributeIndexes:Enabled` routes to them with JSON fallback (log 70021); filter operands over **1000** characters → **400** `filter.valueTooLong`, and `GetInstancesTask` fails on them.
- **`interaction.longPoll.rule`** — a condition script alternative to `roles`, never both, fail-closed on the signal and the ack.
- **`metadata.effectiveStatus`** served on GET, list, `GetInstanceTask` and sync responses, filterable/sortable; served value is `Status.IsTerminal || EffectiveStatus.IsTerminal ? Status : EffectiveStatus`; filters see the raw column.
- **`metadata.type`** (`R` / `S` / `P`), immutable, filterable as `instanceType`; migration `AddInstanceType`.
- **Discovery warm-up** reads `GET {registry}/functions/domain-list` — needs `vnext-discovery-runtime` ≥ 0.0.7; five bulk keys removed, `DomainListEndpointTemplate` / `DomainListExpectedMax` added, `L1TtlSeconds` 60 → 600.
- **Human-task function**: one `UNION ALL` scan per domain, leaf-state `queryRoles` gate, undeclared states dropped (20459), deny-then-allow evaluation, `X-VNext-HumanTask-Truncated` / `X-VNext-Cache-Override` headers, `IX_Instances_HumanTaskV2` replaces the legacy index.
- **18 EventIds renumbered** — update dashboards keyed on the old numbers.
- **Task invocation routing**: `http`, `daprservice`, `soap`, `statestore`, `cacheaside` run on Orchestration by default, per-type `Remote` fallback, restart to apply, `MaxConnectionsPerServer` 50, `LocalInvocationTimeoutSeconds` 60; Orchestration needs the Dapr `state` component; type 22 deprecated; `errorTypes` rules now match on the remote path.
- **Fixes**: stranded-Busy chain reserve released (51 production instances in 30 days), DbMigrator DI crash, outbox continuation carrier.
- **Schema** stays at **0.0.53**.
