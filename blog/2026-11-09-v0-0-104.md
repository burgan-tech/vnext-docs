## Overview

**v0.0.104** is a small, additive release. It has no breaking changes and no database migration.

- **Sync responses carry the instance state**: a sync start or transition answers with `currentState` and `effectiveState` next to `status`, so a sync SubProcess task's output now holds the child's state ([#1185](https://github.com/burgan-tech/vnext/pull/1185), [#1182](https://github.com/burgan-tech/vnext/issues/1182)).
- **Human-task rows carry `dueBy` and `priority`**, read from the leaf instance's `humanTask` data ([#1178](https://github.com/burgan-tech/vnext/pull/1178)).
- **Fix: `authorize?queryRoles` while a SubFlow child is being created**: the deepest existing instance now decides instead of answering `403` ([#1184](https://github.com/burgan-tech/vnext/pull/1184), [#1181](https://github.com/burgan-tech/vnext/issues/1181)).
- **Fix: an ignored FanOut item keeps the inner task's error code**, so an `OutputHandler` can tell a `409` from any other failure ([#1180](https://github.com/burgan-tech/vnext/pull/1180), [#1176](https://github.com/burgan-tech/vnext/issues/1176)).
- **Fix: `modifiedAt` moves with every transition and every `updateData` data row** ([#1183](https://github.com/burgan-tech/vnext/pull/1183)).
- **Performance**: fewer database commands per transition hop ([#1177](https://github.com/burgan-tech/vnext/pull/1177)).

Component **schema 0.0.59** is unchanged.

## Features

### Sync responses carry `currentState` and `effectiveState` (#1185, #1182)

A **sync** start or transition (`?sync=true` or `executionType: S`) now answers with the instance's own state:

```json
// POST .../instances/start?sync=true — 200
{
  "id": "8d83…",
  "status": "A",
  "effectiveStatus": "A",
  "currentState": "otp-waiting",
  "effectiveState": "otp-waiting"
}
```

- The names and values match the instance GET's `metadata.currentState` / `metadata.effectiveState`. They are persisted columns; there is no SubFlow descent, so they are **not** the state function's `state`.
- The runtime-internal answer used for cross-domain `sub/instances/start` and subflow forward carries them too. A **sync SubProcess task** output therefore holds the child's state:

```csharp
// SubProcess (sync) output mapping
var state = context.Body?.data?.value?.currentState   // same-domain start
         ?? context.Body?.data?.currentState;         // cross-domain start
```

- An async `202` carries neither field. No database read was added; the sync response's representation ETag changes once because the body has new fields.

→ [Async/Sync](/docs/how-to/async-sync) · [Workflow](/docs/components/workflow) · Lab: [`SyncSubProcessStateLab`](https://github.com/burgan-tech/vnext-example/pull/54) (vnext-example)

### Human-task rows: `dueBy` and `priority` (#1178)

Each row of `GET /api/v1/{domain}/functions/human-task` carries two optional fields beside `title` and `description`. Both are read from the `humanTask` object in the **leaf** instance's latest data, and they travel through the cross-domain leaf answer too.

```json
{
  "humanTask": {
    "title": "50.000 TL EFT onayı",
    "dueBy": "2026-11-10T17:00:00+03:00",
    "priority": 1
  }
}
```

| Field | Accepted in data | Served as |
|---|---|---|
| `dueBy` | ISO 8601 date (`2026-11-10`) or date-time string | date-time with offset |
| `priority` | JSON number, or a numeric string with a `.` decimal point (`"1.5"`) | number |

- Absent or malformed values (`"next week"`, `"1,5"`, an object) are served as `null`; the row is still listed.
- Ordering is unchanged: `createdAt`, newest first.
- The response cache key moves from `human-task:v1` to `v2`, so entries without the new fields are not served after deploy.

→ [Human Task Approval](/docs/how-to/human-task-approval)

## Fixes

### `authorize?queryRoles` while a SubFlow child is being created (#1184, #1181)

A parent commits its SubFlow correlation in its own transaction; the child's row is created afterwards by a post-commit job. A `queryRoles` probe that landed in that window descended to a child that could not be loaded. The child answered `false` without evaluating a grant, the parent passed it up, and the gateway answered `403` to the client's state poll.

- **Now:** the deepest **existing** instance decides with its own `queryRoles` resolution (stamped parent override → state `queryRoles` → workflow `queryRoles`). That is also what the `state` function serves in that window.
- The authorize response gains an optional field, `reason: "instance-not-found"`. It is set only when the addressed instance could not be loaded (still `403`, no grant evaluated). An ordinary decision is `{"allowed": true|false}` as before.
- Only `queryRoles` falls back. A `transitionKey` / `functionKey` forwarded to a missing child stays refused. A child on an older runtime omits the field, and the previous behaviour applies.
- Observability: log `AuthorizeLeafMissingFallback` (EventId 50046) and span tag `vnext.auth.fallback = leaf-missing` on `Authorization.Decide`.

→ [Authorization](/docs/concepts/authorization) · Lab: [`AuthorizationChainLab`](https://github.com/burgan-tech/vnext-example/pull/53) (vnext-example)

### An ignored FanOut item keeps the inner error (#1180, #1176)

A FanOut item whose own `errorBoundary` resolves the inner task's failure with `Ignore` (`3`) or `Log` now reaches `IFanOutMapping.OutputHandler` with what the inner task answered:

| `FanOutItemResult` | Up to v0.0.103 | v0.0.104 |
|---|---|---|
| `ErrorCode` | `FanOut:ItemFailed` | `Task:{taskType}:{taskKey}:{status}`, e.g. `Task:DirectTrigger:notify-finalize:409` |
| `ErrorMessage` | `FanOut item <key> failed.` | the inner task's message |
| `Data` | `null` | the inner task's response body, when it has one |

Failures handled by a blocking action (`Abort`, `Rollback`, …) and failures with no boundary at all are unchanged.

> **Check your `OutputHandler`s.** A handler that matched `FanOut:ItemFailed` to detect ignored refusals must match the inner status code instead (for example `:409` / `:404`).

→ [FanOut Task](/docs/components/tasks/fan-out) · Lab: [`fan-out-config-matrix`](https://github.com/burgan-tech/vnext-example/pull/52) (vnext-example)

### `modifiedAt` moves with every transition and data change (#1183)

Before, only the set-based status writes (Busy flip and release, un-fault, effective-status projection, long-poll arm) moved `Instances.ModifiedAt`. A completed, cancelled or faulted instance kept a time from before its final transition, and an `updateData` did not move it at all.

- **Now** every transition stamps it, same-state ones included (a completion gets the same instant as `completedAt`). Every data row an `updateData` writes stamps it too, as does a stage, tags or key change. An `updateData` that changes none of these moves nothing.
- `modifiedAt` filters and sorts see the new values. Rows written before the upgrade keep their old values.
- If you read `modifiedAt` as "last status change", re-check that consumer: it now means the last transition or data change.

→ [Instance Filtering](/docs/how-to/instance-filtering)

## Performance

### Fewer database commands per transition hop (#1177)

A transition hop issued more database commands than its work needed. Five are gone, and what is persisted is the same:

- The transition-record INSERT no longer carries a second `UPDATE Instances SET "Status"`; sync reserve already committed the Busy flip.
- Admission reserves with the instance the pipeline already loaded and re-reads only when the CAS is lost.
- Timer cancellation probes with a lean load; under `LatestOnlyInstanceLoading` the tracked load takes two commands instead of three; SubFlow resume skips the Busy CAS when the parent is already Busy.

Measured with the vnext-example `db-cost-lab`: a manual start/submit/complete drops from 12/10/12 to 10/8/10 commands, and a three-level chain finish from 67.5 to 61.2. Commit count per hop and WAL fsyncs are unchanged.

- **Sync responses** carry `currentState` / `effectiveState`; a sync SubProcess output holds the child's state.

- **Fixes:** `queryRoles` no longer denies while a SubFlow child is being created; an ignored FanOut item keeps its inner error code; `modifiedAt` tracks every transition and data change.
- **Performance:** fewer database commands per transition hop.
- **Schema** stays at **0.0.59**.
