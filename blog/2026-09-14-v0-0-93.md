## Overview

This release completes the per-instance history family and trims what the runtime carries. **Two new system functions expose the task journal** — `GET .../instances/{id}/functions/tasks` returns every task that ran on an instance, in execution order, and `GET .../functions/actions?taskId=` returns one task's recorded sub-steps — both metadata-only, both behind the same `queryRoles` gate as the state function ([#981](https://github.com/burgan-tech/vnext/pull/981)). **The Monitor API host is removed** (`/api/v1/monitor`, port `4203`) and the Dapr footprint is pruned to what each host actually consumes: `lock` leaves execution/inbox/outbox, `state` leaves inbox/outbox, `pubsub-broadcast` leaves execution/inbox, the eager `AddRedis()` multiplexer and `dapr-placement` go with them, and the execution host's store names finally match the provisioned components ([#982](https://github.com/burgan-tech/vnext/pull/982)). **Long-polling clients now see the subflow chain's status**: a new `Instances.EffectiveStatus` column joins the state-function fingerprint, and a per-instance notification sequence replaces the wall-clock guard that could drop the notification taking an ancestor out of Busy — on preprod the served body had been built **142 seconds** earlier ([#983](https://github.com/burgan-tech/vnext/pull/983)). **Sync `start` / `transition` responses stop evaluating Extensions** — the `extensions` key stays as an always-empty map and the `?extensions=` parameter on those two endpoints is ignored, removing an extension task round plus a full `ScriptContext` build from every sync transition for a field no client read ([#984](https://github.com/burgan-tech/vnext/pull/984)). And **the span tree now reaches every non-pipeline route** — read envelopes, authorization, the cross-domain hop, the function cache, the events endpoint and the Inbox forwarder — with a startup `ActivitySourceRegistrationCheck`, a corrected collector filter and Aether **1.0.41** closing the last orphaned sidecar spans ([#986](https://github.com/burgan-tech/vnext/pull/986)). This release runs on component **schema 0.0.53**.

## Features

### Task and action history system functions (#981)

An instance's history was readable for transitions (`…/transitions`) and, since v0.0.92, for incidents (`…/incidents`) — but not for what ran *inside* those transitions. The task journal (`InstanceTasks`) existed in the database and nothing public served it.

Two `IInstanceFunctionHandler` registrations complete the family. They are dispatched by the `{function}` route segment like `state`, `data` and `hierarchy`, so a custom function named `tasks` or `actions` is shadowed — the same rule every system function key has always had. `{instance}` accepts the instance id or the business key.

| Function | Returns |
|---|---|
| `GET /{domain}/workflows/{workflow}/instances/{instance}/functions/tasks` | The instance's full task journal, in execution order (`StartedAt` ascending) |
| `GET /{domain}/workflows/{workflow}/instances/{instance}/functions/actions?taskId={id}` | One journal row's recorded execution sub-steps, in execution order |

Both responses are **unpaged** — a task list is bounded by the instance's own transition count, and actions by one task's sub-steps. Each task item projects one journal row joined with its owning transition's context:

```json
{
  "items": [
    {
      "id": "6f9c…",
      "taskKey": "send-otp",
      "transitionKey": "approve",
      "fromState": "draft",
      "toState": "approved",
      "triggerType": "manual",
      "status": "completed",
      "businessStatus": "success",
      "startedAt": "…",
      "finishedAt": "…",
      "durationMs": 184.2,
      "error": null
    }
  ]
}
```

- `toState` is `null` while that transition is still in progress. `status` is the platform status (`waiting | busy | completed | faulted`); `businessStatus` is the business outcome (`unknown | success | failed`).
- **Metadata only, deliberately.** The journal's `Request`, `Response` and `InvocationResult` payloads are not exposed: mapping scripts write the headers they build — including auth material resolved from secret stores — into those columns, so full payloads are operator material and are read from the journal table (or APM) directly. The one payload-derived field is `error`, the fault reason of a faulted row — never a stack trace. The repository projects the metadata columns in the SQL `SELECT` itself, so the jsonb payload columns are not read for this function at all.
- **Authorization** is the same `queryRoles` check as the state function: a caller who may poll an instance's state may read what ran on it. Failing the gate is **403**, so "nothing ran" stays distinguishable from "not allowed to know".
- `actions` takes the owning journal row id (the `id` of a tasks item) as the `taskId` query parameter. Missing or non-GUID → **400** (`Instance:100039`). The function verifies the addressed task belongs to the instance in the route and answers **404** (`Instance:100038`) otherwise — a task can never be read through another instance's role gate.
- No state-function involvement: the state body carries no task links, so `ResponseShapeVersion` is untouched and nothing new participates in the fingerprint ETag. Both functions always answer for the addressed instance only — no subflow descent, no gateway plumbing.

:::note
**Known gap: no writer for actions.** Nothing in the runtime records `InstanceAction` rows today, so the actions function returns an empty list for every task. The read contract is in place for when a writer lands; recording sub-steps from the task engine is its own design decision.
:::

> **Reference:** PR [#981](https://github.com/burgan-tech/vnext/pull/981) — see also [Built-in Functions](/docs/components/functions/built-in) and [REST API](/docs/api-reference/rest-api).

### Monitor API host removed, Dapr components pruned (#982)

Two cleanups driven by one audit: **which host actually consumes which Dapr building block**. The audit followed consumption points in code — the type that injects the abstraction, or the `DaprClient` call — not DI registrations, because a registration is lazy and proves nothing. Every component a sidecar loads costs a client and a connection pool whether or not the application ever calls it.

**The Monitor API host is gone in full.** The read-only Monitor API (`/api/v1/monitor`, port `4203`) is removed: both projects, its test project, `etc/monitoring/` (six Dapr components plus sidecar config), the compose services and env files, the `run-docker.sh` `--monitor` flag and `docs/monitoring/`. The Helm chart never had a monitoring deployment and CI never built its image, so neither needed a change. `docs/monitoring/correlation-and-tracing.md` turned out to be the runtime's tracing contract rather than Monitor documentation, and moved to `docs/runtime/`.

**The resulting footprint:**

| | orchestration | execution | inbox | outbox | db-migrator |
|---|---|---|---|---|---|
| **state** | ✅ | ✅ *domain tasks only* | ❌ | ❌ | ❌ |
| **lock** | ✅ | ❌ | ❌ | ❌ | ✅ |
| **pubsub** | ✅ *one publish* | ⚠️ domain-authored only | ✅ | ✅ | ❌ |
| **pubsub-broadcast** | ⬜ kept, unused | ❌ | ❌ | ❌ | ❌ |
| **configuration** | ⬜ kept, unused | ⬜ | ⬜ | ⬜ | ⬜ |
| **bindings** | ✅ notification | ⚠️ domain-authored only | ❌ | ❌ | ❌ |
| **jobs** | ✅ | ❌ | ❌ | ❌ | ❌ |

- `lock` is dropped from **execution, inbox and outbox** — it stays on orchestration (Busy mutex, resource locks, discovery, schema migration) and db-migrator (`SchemaMigrationOrchestrator`). The execution host's `AddDistributedCache` / `AddDistributedLock` calls go with it; nothing in that process resolved either abstraction.
- `state` is dropped from **inbox and outbox** — it stays on orchestration (component/state/data caches) and execution, where `StateStoreTask` / `CacheAsideTask` fall back to `DAPR_STATE_STORE_NAME`.
- `pubsub-broadcast` is dropped from **execution and inbox** and **deliberately kept on orchestration** for a planned pod-to-pod invalidation path. `configuration` (`vnext-config`) is untouched everywhere by decision, though the Dapr Configuration API is never called. Both are recorded so a future audit does not "discover" them again.
- **`AddRedis()` is removed** from orchestration, execution and db-migrator. It opens an eager `ConnectionMultiplexer` at startup and vNext has no `IConnectionMultiplexer` consumer anywhere — three hosts held an unused Redis pool plus an avoidable startup dependency. The `Redis` appsettings sections and `Redis__*` env entries go with it. The Redis *server* stays: it backs the Dapr state/lock/pubsub components.
- **Dapr placement is removed.** No actor code exists and every state component sets `actorStateStore: "false"`, so the `dapr-placement` container, every `--placement-host-address` sidecar argument and the `DAPR_PLACEMENT_HOST` env key are gone. `dapr-scheduler` stays — orchestration's background jobs run on the Dapr Jobs API.
- **A latent store-name bug is fixed.** `.env.execution.dev` / `.stage` and `etc/execution/dapr/config.yaml` named `vnext-execution-{state,pubsub,secret}` while the provisioned components are `vnext-{state,pubsub,secret}`. Latent so far — `Vault:Enabled` is `false` locally and no example flow authors a `StateStoreTask` without an explicit `storeName` — but the secret-store scope would have failed the execution host at startup the moment Vault was switched on.

The evidence per cell, the components deliberately kept though unused, and the grep recipes to re-derive the map live in the new `docs/runtime/dapr-component-footprint.md` in the runtime repo. Two pubsub name differences are correct and must be left alone: `vnext-pubsub-inbox` / `vnext-pubsub-outbox` versus orchestration's `vnext-pubsub` (a component name is local to the sidecar; the Redis Streams key is the topic), and the inbox/outbox sharing `consumerID: "vnext-workers"` (consumer groups are per-stream, and the two subscribe to disjoint topics).

:::warning
Helm work is **not** in this release — `vnext-helm-charts` is a separate repository. The mirrored work list is in the footprint doc: component `scopes:` (the platform components currently have none, so every daprd in the namespace loads all of them), per-app `DAPR_*` env out of `vnext.commonEnvVars`, `actors.enabled: false`, and the dead `Redis__*` configmap entries.
:::

> **Reference:** PR [#982](https://github.com/burgan-tech/vnext/pull/982) — see also [Caching](/docs/configuration/caching) and [Service discovery configuration](/docs/configuration/service-discovery).

### Subflow chain status visible to long-polling clients (#983)

A client posts an async transition to a parent sitting in an active subflow, gets its 202, polls the state function — and is told the flow is `Active`, in the state it was in before, with the transition it just accepted still listed. It follows that body's view link and gets a 404. Preprod, 2026-09-10, runtime 0.0.92: the served body had been built **142 seconds earlier**.

The accept was not at fault. It reserved the chain correctly — the leaf went Active → Busy under the status lock before the 202 committed. The problem was that **nothing it wrote was visible to the poller's validation**: a parent holding an open SubFlow correlation is Busy for that subflow's whole lifetime by design, so its own status never moves; its correlation rows are untouched; `SubFlowStateChangedAt` only moves when the child reports a *state* change. The parent's fingerprint was bit-identical before and after the accept, and the active-subflow snapshot cached against it stayed valid across exactly the transition it must not survive. No TTL protected that window either: the Dapr cache provider truncates a sub-second TTL to `0` and omits the `ttlInSeconds` metadata entirely, so the "500 ms" snapshot was written with no expiry at all.

**`Instance.EffectiveStatus`** — the status counterpart of `EffectiveState`: the status a client polling *this* instance would observe (the deepest active SubFlow's, else its own), folded into `InstanceStateFingerprint` and the state-function ETag material. Two propagation edges maintain it:

- **Down (synchronous).** The busy walk already visits every level, locally and cross-domain; it now carries the leaf's resulting status back up the call stack and stamps each ancestor with it. At the bottom of the chain the projection rides in the same CAS as the status flip. A far side that reports nothing is read as *unknown, write nothing* — never as Busy.
- **Up (event).** A sub-item leaving Busy at its own rest point reaches ancestors as a notification that now carries the status — and is finally sent in the case that used to send nothing: an episode ending in the state it started in (a `$self` shared transition, a retry, or a long-poll interaction resuming after its acknowledgement). Before this, every ancestor the accept had stamped Busy stayed Busy with no later event able to correct it.

**Ordering no longer depends on a clock.** The receiver rejected notifications by `ChangedAt`, a wall clock from whichever pod ran the child. Under skew a legitimate notification was discarded, and if it was the one taking an ancestor out of Busy the result was a client long-polling a chain that had already finished — the one failure here that does not self-heal. A per-instance notification counter (`Instances.SubStateNotificationSeq`, incremented inside the transaction that publishes) matched by a watermark on the correlation (`InstancesCorrelations.SubFlowNotificationSeq`) replaces it. Equal is still a duplicate and re-applied idempotently; sequences are compared only when both sides carry one, so a publisher that predates the counter — the other half of a rolling deploy — falls back to the timestamp guard.

**Authority is deliberately narrow in this release.** `EffectiveStatus` is fingerprint material only — never served, never read by a decision. The served status still comes from the live subflow descent, which keeps a missed propagation *fail-stale* (a cached body survives a moment too long) instead of *fail-wrong*. The full-build path logs the drift between the projection and the live value (`EffectiveStatusDrift`, EventId **20445**) — the evidence needed before it is promoted to a served value.

Measured with the regression suite in `vnext-example` (`SubflowStatusProjectionTests`, 11 tests): **11/11 green** on this release, **5 red** against a runtime built from the previous master — including the preprod defect reproduced locally (`Expected: "B", Actual: "A"`) and the long-poll interaction path, which was the most user-visible instance of the missing release: a client that rendered the interaction screen and acknowledged was still shown a Busy chain, permanently.

> **Reference:** PR [#983](https://github.com/burgan-tech/vnext/pull/983) — see also [Async & sync](/docs/how-to/async-sync) and [Built-in Functions → State](/docs/components/functions/built-in).

### Sync responses no longer evaluate Extensions (#984)

A `sync=true` `start` or `transition` no longer evaluates the workflow's **Extensions** while projecting its response. Nothing read it: the client workflow manager never consumed `extensions` off a write response, and a service-to-service caller already receives `attributes`. Extensions are *enrichment*, not data — anyone who needs a value asks a read surface for it. The pass was not free: every sync transition paid an extension task round (HTTP calls included) **plus** a `ScriptContext` build, which serializes the instance's whole latest data, for a field no client read.

- The `extensions` key **stays on the response as an always-empty map**, so the response shape is unchanged for existing clients. Leaving it null would drop the key entirely under `WhenWritingNull`; keeping it empty preserves the contract.
- `InstanceCommandAppService.EnrichOutputCoreAsync` is the single seam: the `ProcessExtensionsAsync` call is gone and `IInstanceExtensionService` is removed from the constructor, so the guarantee is enforced by the compiler rather than a flag. Extensions were the only other consumer of the projection's `ScriptContext`; building one is now gated on `workflow.Output is { HasMappingCode: true }`, so a workflow without an output script builds none. **That is the perf half of the change.**
- The `?extensions=` query parameter is removed from `StartAsync` / `TransitionAsync`, from `StartInstanceInput` / `TransitionInput`, from the internal `sub/instances/start` endpoint (which bound it only to discard it) and from the cross-domain forwarding in `RemoteInstanceCommandAppService`. An old caller that still sends it is **not rejected** — ASP.NET does not reject an unbound query parameter — it just stops getting extensions back. Pinned by an integration test.
- **The read path is untouched.** `InstanceQueryAppService` still runs extensions on all four read surfaces: instance GET, instance list, the data function and the extensions endpoint.
- Dead after the removal: `WorkflowLogs.ExtensionProcessingFailedNonBlocking` and the `vnext.extensions.requested` span tag; `Instance.EnrichResponse` no longer has an `Extension.Process` child.

Verified end to end against `loan-disbursement`, the one example flow with a workflow-level extension (`customer-profile-enrichment`, `type=3 DefinedFlows`, `scope=1 GetInstance`): `SyncResponseExtensionsTests` **4/4** on this release, **3 red** on the previous master — with the fourth case asserting that the instance GET and data function still return `customerProfileEnrichment.customerProfile`, green on both.

> **Reference:** PR [#984](https://github.com/burgan-tech/vnext/pull/984) — see also [Extensions](/docs/components/extension) and [Async & sync](/docs/how-to/async-sync).

### Span tree on every non-pipeline route (#986)

The transition pipeline's span discipline now extends to the rest of the API surface. Before this, the read path, authorization, the cross-domain hop, the function cache, the events endpoint and the Inbox forwarder all landed unattributed on the ASP.NET server span — and because built-in and custom functions share one route template, a state poll, a view read and a custom-function call were indistinguishable in APM. Scope was set by a council session that cut the proposal from ~40 span families to **8 approved + 6 conditional**; everything in that catalogue is now live.

**New spans:** read envelopes (`Instance.Read/{kind}`, a closed set), `Remote.Send/{client}`, `Auth.Decide`, `Auth.FilterTransitions`, `Auth.PreviousUserLookup`, `View.Resolve`, the function path's `Schema.Validate`, `Event.Intake`, `Inbox.Forward`, function-cache `Cache.Get` / `Cache.Set`, and `Instance.Read.BuildGate`.

**The hot path costs zero span documents.** The state/data 304 and cache-hit branches create **no** vNext activity at all; the discriminator travels as `vnext.function.key` + `vnext.read.fastpath` on the transaction, written on every branch. Measured live: 233 `cacheHit` transactions produced **0** `Instance.Read/state` spans, 6 `build` produced exactly 6.

**Four defects repaired**, each a violation of a standing precedent rather than new design:

1. `JobTimeoutRecoveryService` emitted **three** `Instance.Activation` spans per recovered timeout. Its tests never caught it because they mocked `BeginAsync` while the service calls the synchronous `Begin`, so every test silently exercised the catch block.
2. `InstanceSubStateChangedEvent` was not lane-aware, so a cross-domain sub-state relay detached from the child's trace lane. It now carries all six carrier fields.
3. `ChildSubflowFaultService` opened no span while its cancel twin did.
4. `TransitionContinuationRequestedEventHandler` set no root-instance baggage.

**Two guards instead of ~40 per-span tests.** A build-time check verifies every declared source is registered per host (with deliberate per-host omissions encoded in Domain), and a startup `ActivitySourceRegistrationCheck` reads the *merged* `Telemetry:Tracing:AdditionalSources` configuration. .NET merges config arrays by index, so one `AdditionalSources__0` in a chart's env block silently *replaces* the first source rather than appending; a repository-level test cannot see that, this one can. It found a real defect on its first deployment — the cross-domain lab's generated appsettings had drifted and lost sources, so `Remote.Send` silently did not exist there.

**A collector fix.** `filter/dapr-internals` matched `^/?dapr\.proto…`, and the optional slash dropped the **app's own** gRPC client span too — the one its comment said must survive. Measured: zero spans of either kind through that collector, against 254 + 254 through one without it. The pattern is now anchored to `^/`, so only the sidecar's server span is dropped and `Cache.Get` / `Lock.Acquire` show their wire time again.

**One upstream dependency shipped.** The orphaned Dapr sidecar spans were Aether filtering the HttpClient span *after* its id had been written to the wire. Fixed in Aether and released as **1.0.41**, which this release targets. Three plausible fixes were measured and refuted first and are written down in the evidence page so nobody spends the same hours. Consequence: `filter/dapr-internals` is now a **volume** choice rather than a correctness one — and ordering matters, because removing it from an environment still on the old Aether brings the orphans back.

> **Reference:** PR [#986](https://github.com/burgan-tech/vnext/pull/986) — see also [Observability](/docs/how-to/observability) and [Telemetry configuration](/docs/configuration/telemetry).

## Behavior Changes

Three items change what a deployment or a client observes. **The Monitor API host is gone** — any ingress, gateway route or helm value still pointing at `/api/v1/monitor` on port `4203` must be removed, and the journal payloads it served are now read from the database or APM. **The Dapr prune** removes env keys (`Redis__*`, `DAPR_PLACEMENT_HOST`, `DAPR_LOCK_STORE_NAME` on execution, `DAPR_STATE_STORE_NAME` on inbox/outbox, `DAPR_PUBSUB_BROADCAST_STORE_NAME` on execution/inbox/outbox) and renames the execution host's store references from `vnext-execution-*` to `vnext-*`; a deployment that provisions its own components needs the same alignment. And **sync `start` / `transition` responses carry an always-empty `extensions` map**, with `?extensions=` on those two endpoints ignored rather than rejected — the read surfaces are unchanged. Each item, its impact direction and the migration steps are documented in the [v0.0.93 breaking changes announcement](/blog/breaking-changes/breaking-changes-v0-0-93).

## Fixes

- **A parent in an active subflow no longer serves a stale Busy/Active status to a long-poller** — `EffectiveStatus` joins the fingerprint, the busy walk stamps ancestors on the way down, and the rest-point notification carries the status on the way up ([#983](https://github.com/burgan-tech/vnext/pull/983)).
- **A status-only episode now moves the ETag** — an episode ending in the state it started in (`$self` transition, retry, long-poll acknowledgement) used to send no notification, leaving every ancestor the accept had stamped Busy permanently Busy ([#983](https://github.com/burgan-tech/vnext/pull/983)).
- **Sub-state notifications are ordered by a sequence, not a wall clock** — under pod skew a legitimate notification could be discarded; the receiver now compares `SubStateNotificationSeq` against its correlation watermark and falls back to the timestamp guard only for seq-less publishers ([#983](https://github.com/burgan-tech/vnext/pull/983)).
- **The execution host's Dapr store names resolve** — `vnext-execution-{state,pubsub,secret}` referenced components that did not exist; the secret-store scope would have failed the host at startup the moment Vault was enabled ([#982](https://github.com/burgan-tech/vnext/pull/982)).
- **A recovered timeout emits one `Instance.Activation` span, not three**; a cross-domain sub-state relay stays in the child's trace lane; `ChildSubflowFaultService` opens a span; the continuation handler sets root-instance baggage ([#986](https://github.com/burgan-tech/vnext/pull/986)).
- **The collector no longer drops the app's own Dapr gRPC client span** — the `filter/dapr-internals` pattern is anchored to `^/` ([#986](https://github.com/burgan-tech/vnext/pull/986)).
- **Sidecar spans no longer orphan** — Aether 1.0.41 applies the diagnostic-request filter at injection time, so the sidecar's span parents on the exported gRPC client span ([#986](https://github.com/burgan-tech/vnext/pull/986)).

```json
{
  "runtimeVersion": "0.0.93",
  "schemaVersion": "0.0.53"
```

> **Note:** Schema version is unchanged at **0.0.53**.

**Removed settings and env keys** ([#982](https://github.com/burgan-tech/vnext/pull/982)):

- **`Redis` configuration section and `Redis__*` env entries** (e.g. `Redis__Standalone__EndPoints__0`) on orchestration, execution and db-migrator — `AddRedis()` is gone and nothing binds them. The Redis server itself stays for the Dapr components.
- **`DAPR_PLACEMENT_HOST`** on every host, together with the `dapr-placement` container and `--placement-host-address` sidecar arguments.
- **`DAPR_LOCK_STORE_NAME`** on execution; **`DAPR_STATE_STORE_NAME`** on inbox and outbox; **`DAPR_PUBSUB_BROADCAST_STORE_NAME`** on execution, inbox and outbox — each named a component that host no longer loads.
- The execution host's `DAPR_STATE_STORE_NAME` / `DAPR_PUBSUB_STORE_NAME` / `DAPR_SECRET_STORE_NAME` now read `vnext-state` / `vnext-pubsub` / `vnext-secret`, matching the provisioned components.

**Telemetry.** `Telemetry:Tracing:AdditionalSources` is now checked at startup by `ActivitySourceRegistrationCheck` against the merged configuration; a chart env block that sets `AdditionalSources__0` replaces the first source rather than appending, and the check makes that visible ([#986](https://github.com/burgan-tech/vnext/pull/986)). Dapr sidecar `config.yaml` no longer carries a placement address.

**Migrations.** `AddInstanceEffectiveStatus` adds `Instances.EffectiveStatus` (`varchar(3)`, default `'A'`) and backfills every row from its own `Status` — a parent currently inside an active SubFlow ends up with its own status rather than the leaf's until the first flip or upward notification restamps it, which is a transient over-fresh value, never a stale Busy, and cannot produce a wrong response because the column is not served in this release. `AddSubStateNotificationSeq` adds two `bigint` watermarks, `Instances.SubStateNotificationSeq` and `InstancesCorrelations.SubFlowNotificationSeq`, both defaulting to `0` = "not reported" so events already in flight during the rollout keep working. Both run per schema; both are additive and backward compatible with an older runtime reading the same database ([#983](https://github.com/burgan-tech/vnext/pull/983)).

**Container images:** published at tag `0.0.93` under `ghcr.io/burgan-tech/vnext/*` (`execution`, `orchestrator`, `init`, `inbox`, `outbox`, `db-migrator`, `mcp-server`, `python-runner`), Cosign-signed (keyless OIDC) with SBOM + provenance. There is no longer a monitoring image to publish. Immutable digests are listed in the [GitHub release](https://github.com/burgan-tech/vnext/releases/tag/v0.0.93).

## Summary

- **Task and action history** — `GET …/functions/tasks` (full journal, execution order, unpaged) and `GET …/functions/actions?taskId=` (one task's sub-steps); metadata only, `queryRoles`-gated, `400 Instance:100039` without a valid `taskId`, `404 Instance:100038` for a task of another instance. No writer for actions yet.
- **Monitor API host removed** (`/api/v1/monitor`, port `4203`); Dapr `lock` / `state` / `pubsub-broadcast` pruned per host, `AddRedis()` and `Redis__*` gone, `dapr-placement` and `DAPR_PLACEMENT_HOST` gone, execution store names aligned to `vnext-*`.
- **Long-pollers see the chain's status** — `EffectiveStatus` in the fingerprint, propagated down on the busy walk and up at the rest point; sequence-ordered notifications replace the wall-clock guard. Drift sentinel `EffectiveStatusDrift` (20445).
- **Sync `start`/`transition` skip Extensions** — `extensions` is always `{}`, `?extensions=` ignored on those endpoints; read surfaces unchanged; no `ScriptContext` without an output script.
- **Span tree on every route** — read envelopes, `Auth.*`, `Remote.Send`, `View.Resolve`, `Event.Intake`, `Inbox.Forward`, `Cache.Get/Set`; zero spans on the 304 / cache-hit path; startup `ActivitySourceRegistrationCheck`; collector filter anchored to `^/`; Aether **1.0.41**.
- **Migrations** `AddInstanceEffectiveStatus` and `AddSubStateNotificationSeq`, both additive.
- **Schema** stays at **0.0.53**.
