## Overview

**v0.0.106** makes losing a resource-lock race survivable and fixes an out-of-memory failure in component version resolution. It has **no breaking changes** and no database migrations.

- **`onConflict: "Reject"`**: a transition that loses a lock race answers `409 Execution:200014` and leaves the instance untouched, so the caller can repeat the same call ([#1143](https://github.com/burgan-tech/vnext/pull/1143)).
- **Error boundary routes lock conflicts**: an `errorBoundary` rule for `Execution:200010` can send the loser down another transition instead of faulting it ([#1143](https://github.com/burgan-tech/vnext/pull/1143)).
- **Postgres lease provider**: `ResourceLock:Provider = postgres` stores locks in Postgres, where `Extend` works ([#1143](https://github.com/burgan-tech/vnext/pull/1143)).
- **Locks are released on commit** of the terminal state, and a new hold-duration metric shows locks that are released late ([#1143](https://github.com/burgan-tech/vnext/pull/1143)).
- **Fixes**: resolving a floating component version (`1.0.0`, `1`, `latest`) no longer loads the body of every stored version, which ran pods out of memory and served old versions without an error ([#1303](https://github.com/burgan-tech/vnext/pull/1303)); publishing no longer loads every stored version either ([#1304](https://github.com/burgan-tech/vnext/pull/1304)).

Component **schema 0.0.61** ships with this release. Its only change adds `Reject` to `resourceLock.onConflict`.

## Features

### `onConflict: "Reject"` — lose the race without losing the instance (#1143)

Until now `Abort` was the only conflict policy: the losing transition faulted the instance and the caller got `409`. The contended work was gone, and a retry meant starting a new instance. `Reject` treats a lost race as "not your turn" instead:

```json
"resourceLock": {
  "keyExpression": { "location": "./src/LimitLockKey.csx", "code": "<script>", "type": "L", "encoding": "NAT" },
  "action": "Acquire",
  "ttlSeconds": 300,
  "onConflict": "Reject"
}
```

| Policy | Instance after the conflict | Caller gets | How to retry |
|---|---|---|---|
| `Abort` (default) | **Faulted** (`F`) | `409 Execution:200010` | Start a new instance |
| `Reject` | Unchanged, still Active in the same state | `409 Execution:200014` | Repeat the **same** call once the lock frees |

- The lock step runs before `OnExecute`, `OnExit`, the state change and `OnEntry`, so nothing has been written when the conflict is detected. The Busy reservation the request took is handed back before the `409` returns.
- The two codes are different on purpose: a client can tell "your instance died" from "someone else holds it right now".
- `Reject` is logged at Information level as `TransitionRejectedWithoutFaulting` (EventId `10263`).

→ [Resource Lock](/docs/how-to/resource-lock) · Lab: [`resource-lock-lab`](https://github.com/burgan-tech/vnext-example/pull/59) (vnext-example)

### Error boundary reroutes a lock conflict (#1143)

A domain that does not want to answer the caller with `409` can leave `onConflict` at `Abort` and add an `errorBoundary` rule for `Execution:200010`. When the rule names a `transition`, the instance is **rerouted** to it instead of faulted:

```json
"errorBoundary": {
  "onError": [
    {
      "action": 0,
      "errorCodes": ["Execution:200010"],
      "transition": "wait-for-lock",
      "priority": 10
    }
  ]
}
```

- The state boundary is checked first, then the workflow's global boundary — the same chain task errors use. One rule can cover both task errors and lock conflicts.
- Rerouting is sound because the instance never left its state. The target transition runs like an automatic hop, and an incident (`errorLayer: Pipeline`) records why; it is resolved when the reroute lands.
- A typical target parks the instance in a waiting state with a timer that tries again later.
- Only lock conflicts are routable this way today. Other pipeline-step failures fault as before.

Publish-time validation catches the wrong wirings:

| Rule | Result |
|---|---|
| `Retry` (`action: 1`) on a rule that names `Execution:200010` or `Execution:200014` | **Error** — the retry runs while the lock is still held, so every attempt fails the same way |
| A state boundary handling a lock code routes to a transition not available from that state | **Error** (a **warning** for rules that do not name a lock code) |
| A boundary target transition declares its own `resourceLock` | **Warning** — the ErrorBoundary pipeline profile skips the resource-lock step, so that lock never runs |
| `Acquire` / `Extend` with `ttlSeconds` ≤ 0 | **Error** |

→ [Error Boundary](/docs/how-to/error-handling) · [Resource Lock](/docs/how-to/resource-lock)

### Postgres lease provider for resource locks (#1143)

Resource locks used to go through the Dapr lock building block only. Its Redis component uses `SET NX`, which refuses a re-acquire even from the owner, so `Extend` could not renew a held lock. The runtime now also ships a Postgres lease store, chosen by configuration:

```
ResourceLock__Provider = dapr | postgres        (default: dapr)
```

| Provider | Store | `Extend` | Needs |
|---|---|---|---|
| `dapr` (default) | Dapr lock component (`DAPR_LOCK_STORE_NAME`) | Does not work while the lock is held | The lock component, as before |
| `postgres` | `sys_queues."DistributedLocks"` (key prefix `wfres:`) | Renews the owner's lease | `ConnectionStrings:Default`; no Dapr lock component |

- The default is unchanged. A deployment that sets nothing keeps Dapr.
- An unknown value fails startup (`Unknown ResourceLock:Provider '…'`). An empty value counts as unset. `postgres` without a connection string also fails startup.
- The table is created by the runtime's existing migrations. The Helm chart has no dedicated value yet; set the environment variable on the orchestrator.

→ [Resource Lock § Lock provider](/docs/how-to/resource-lock)

### Locks are released when the terminal state commits (#1143)

When an instance finishes, its locks used to be released by the cleanup event (outbox → Dapr → inbox). If that chain stalled, the lock stayed until its TTL and every waiting instance burned its retries against a holder that had already finished.

The finish step now releases the instance's locks right after the terminal state commits, in the same request. Releasing before the commit could let a second instance in while the transition might still roll back. The event-driven cleanup stays as an idempotent backstop. A release that fails never fails the business transition.

A new histogram shows how long locks are held:

| Metric | Type | Tags |
|---|---|---|
| `workflow_resource_lock_hold_duration_ms` | histogram | `vnext.domain`, `vnext.flow.key` |

Alert on the upper percentiles approaching the configured TTL: that means locks are being freed by expiry, not by release. Acquisition times are stored in instance metadata (`resource.locks.acquiredAt`); instances that acquired a lock before v0.0.106 have none and are not measured.

→ [Observability § Metrics](/docs/how-to/observability)

## Fixes

### Floating version resolution no longer loads every version (#1303)

A component requested by a floating version (`1.0.0`, `1.0`, `1`, `latest` or none) was resolved — on every cache miss and every publish — by loading and deserializing the stored body of **every** published version. On a flow with ~190 versions of ~1.3 MB each, this ran orchestration pods out of memory. Worse, a version that failed to deserialize was silently dropped from the list, so an older version could win and be cached for up to an hour on every pod: starts ran an old flow version with no error.

- The cache now picks the version from the **version strings only** and loads **one** body.
- A winning version that cannot be read fails the request instead of falling back to an older one, and nothing is cached for it.
- A full version without build metadata (`1.0.0-pkg.1.0.123` for a stored `…+core`) is now also found by floating resolution.
- The resolution rules (best match, default-version pointer) do not change.

The component cache key shape moves from `s2` to `s3`, so wrong answers cached by older pods are never read. After the upgrade each component resolves once per pod from the database.

→ [Flow Default Version § Resolution](/docs/concepts/flow-default-version) · [Caching](/docs/configuration/caching) · Lab: [`version-pin-lab`](https://github.com/burgan-tech/vnext-example/pull/64) (vnext-example)

### Publish no longer loads every version (#1304)

`POST /api/v1/definitions/publish` loaded the component with all its stored version bodies just to check whether the version already exists. The publish, seed-data and invalidate-cache paths now check versions by their strings and read at most one body. The responses are unchanged (same `409 Instance:100002` for a duplicate). With both fixes, publishing the 191st version of a 1.37 MB flow peaks at ~0.8 GB instead of ~4.4 GB.

## Upgrade Notes

- **Running 0.0.103–0.0.105 and seeing old flow versions start?** Upgrade. Until then, reference the full version (`1.0.0-pkg.1.0.N+domain`) from consuming flows; restarting pods does not help, because the wrong answer lives in Redis.
- **Cold cache after upgrade:** the cache shape changes to `s3`; each component is resolved once per pod from the database. Old `s2` keys expire on their TTL.
- ⚠️ **New publish validation for resource locks:** `Acquire` / `Extend` with `ttlSeconds` ≤ 0 is now rejected at publish. Check definitions that set `ttlSeconds: 0` before republishing.
- **Log EventIds:** the two new pipeline log messages use `10263` (`TransitionRejectedWithoutFaulting`) and `10264` (`TransitionReroutedByErrorBoundary`).
- **Not changed:** a partial request (`1.0`, `1`, `latest`) can still resolve to a pre-release (`1.0.2-beta.1` beats `1.0.1` by SemVer).

## Summary

- **Resource lock:** `onConflict: "Reject"` returns `409 Execution:200014` and leaves the instance untouched.
- **Error boundary** can reroute a lock conflict (`Execution:200010`) instead of faulting the instance.
- **`ResourceLock:Provider = postgres`** makes `Extend` work; Dapr stays the default.
- **Locks** are released when the terminal state commits; `workflow_resource_lock_hold_duration_ms` shows late releases.
- **Fixes:** floating version resolution and publish no longer load every stored version (no more OOM or silent old versions).
- **Schema** moves to **0.0.61**. No migrations.
