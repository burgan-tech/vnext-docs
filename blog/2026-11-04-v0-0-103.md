## Overview

**v0.0.103** is a focused release, and it has one breaking change.

- **Python Task runs in the domain's own runtime container** ⚠️: PythonTask (type `23`) now names a handler registered in a domain image built `FROM ghcr.io/burgan-tech/vnext/python-runtime`. The Orchestrator calls it directly over Dapr. Python, `pythonnet` and the Kubernetes client are gone from every vNext image ([#1157](https://github.com/burgan-tech/vnext/pull/1157)).
- **Fix: parallel same-domain instance reads**: same-order `GetInstances` / `GetInstance` / `GetInstanceData` tasks reading the same flow no longer share one `DbContext`. Before, one failed, the rest were cancelled, and the flow could silently take the "not found" path ([#1166](https://github.com/burgan-tech/vnext/pull/1166), [#1161](https://github.com/burgan-tech/vnext/issues/1161)).
- **Performance**: one shared EF Core model across flow schemas ([#1159](https://github.com/burgan-tech/vnext/pull/1159)), and fewer round-trips on nested SubFlow start chains and completions ([#1156](https://github.com/burgan-tech/vnext/pull/1156)).
- **Observability**: long-poll resumes are counted and logged by what drove them (`ack` vs fallback) ([#1156](https://github.com/burgan-tech/vnext/pull/1156)). `vnext.flow.version` baggage is now propagation-safe ([#1173](https://github.com/burgan-tech/vnext/pull/1173)).

Component **schema 0.0.59** ships with this release. It adds the PythonTask (type `23`) handler contract.

## Features

### Python Task: domain runtime container (#1157)

*Shipped in v0.0.103. ⚠️ Breaking (PythonTask config, Execution `Python:*` settings).*

PythonTask no longer carries code. A domain that needs Python ships its own runtime image with its handlers and pinned requirements, and enables it in the Helm chart. The Orchestrator calls the handler over Dapr service invocation with a versioned contract (`POST v1/invoke`, contract `1`). There is no Execution hop, and a domain without Python deploys nothing extra.

```
Orchestration ──(InputHandler → invoke → OutputHandler)──▶ Dapr invoke {app-id} POST v1/invoke
                                                              │
                                     python-runtime Deployment (opt-in, per domain)
                                     FROM ghcr.io/burgan-tech/vnext/python-runtime
```

**Handler** (in the domain image):

```python
from vnext_runtime import handler

@handler("risk_score")
def risk_score(input):
    return {"score": min(100, input["income"] // 1000)}
```

**Task** (schema 0.0.59):

```json
{
  "type": "23",
  "config": { "handler": "risk_score", "input": { "income": 85000 }, "timeoutSeconds": 20 }
}
```

**What changes:**
- `config.handler` is required (`^[A-Za-z_][A-Za-z0-9_.-]{0,127}$`). `config.input` and `config.timeoutSeconds` (1–50, default 30) stay. `config.script` and `config.executionMode` are rejected at publish and by the schema.
- The standard `InputHandler` / `OutputHandler` mapping now runs for PythonTask. An input mapping replaces `config.input` with `SetInput`.
- A runtime failure is a failed task result: `StatusCode` is the HTTP status, `ErrorMessage` is `"<code>: <message>"`. Error-boundary rules can match on either. The Orchestrator itself answers `503` when the domain has no runtime, `408` when the runtime does not answer in time, and `413` when the mapped input exceeds 2 MiB.
- The Execution host's `Python:*` section and the `pythonNet` / `process` / `container` modes are removed. Leftover overrides are ignored.
- The base image is published as `ghcr.io/burgan-tech/vnext/python-runtime:0.0.103`. The Helm chart **1.0.127** adds the opt-in `pythonRuntime` block (image, replicas, resources, HPA, NetworkPolicy, `config.*`).

→ [Python Task](/docs/components/tasks/python) · [Python Runtime Configuration](/docs/configuration/python) · [Helm Chart § Python Runtime](/docs/deployment/helm-chart#python-runtime)

## Performance

### One EF Core model across flow schemas (#1159)

`WorkflowDbContext` unit-of-work contexts now share **one** EF Core model. The model is mapped to Aether's schema placeholder, and the command interceptor qualifies each command with the real schema. Before, each flow schema built its own model. EF Core's internal cache holds only about 29 such models with ten query shapes. Domains with more flow schemas kept rebuilding models and recompiling queries on the request path, under a global lock. That showed up as 18–48 ms of unexplained time before the first query on a cold schema.

- The same SQL runs against the same schemas.
- Spans still show the real schema in `db.statement` / `db.query.text`.
- Migration and design-time contexts keep a schema-bound model. The model snapshot is unchanged.

### Nested SubFlow start chains and completions (#1156)

- An intermediate level of a nested SubFlow **start** chain no longer runs a post-commit settle that could change nothing. The client-facing root still settles from the authoritative reload. The skipped settle is tagged `vnext.settle.skipped=true`.
- The completion relay no longer opens a separate unit of work for the `SettledAt` marker; the parent's resume hop stamps it itself.
- Measured on a depth-4 approval chain (test): nine no-op settles of 58 ms, four discarded re-reads of ~100 ms and five marker writes per request are gone. `leaf-finish` p50 at depth 3: 381 → 296 ms.

Persisted state, status transitions, events and the public API are unchanged.

## Observability

### Long-poll resume by trigger (#1156)

A pipeline paused by `interaction.longPoll` (`terminate: true`) resumes either because the client posted `longpoll/ack` or because the `fallbackTimeoutSeconds` job fired. These two used to share one log line and no metric. Now:

| Surface | Ack | Fallback |
|---|---|---|
| Span `LongPoll.AckResume` → `vnext.activation.trigger` | `ack` | `ack-timeout` |
| Metric `workflow_longpoll_resume_total` (meter `BBT.Workflow.Telemetry`) | `trigger=ack` | `trigger=ack-timeout` |
| Log | `LongPollAckResumed` (20301) | `LongPollFallbackResumed` (20308) |

The counter is also tagged `vnext.domain`, `vnext.flow.key` and `vnext.longpoll.ack_resume.outcome`. If a flow's `ack-timeout` count tracks its resume count, its client never acknowledges, and every instance waits the whole window. In the test environment, one approval flow resumed 36 of 36 instances through the fallback.

→ [Async/Sync → Monitoring long-poll resumes](/docs/how-to/async-sync#long-poll-resumeunu-izleme)

### Propagation-safe `vnext.flow.version` baggage (#1173)

vNext writes `vnext.flow.version` to W3C baggage with every character outside the RFC 3986 unreserved set replaced by `_`. For example, `1.0.0-pkg.1.0.346+contract` travels as `1.0.0-pkg.1.0.346_contract`. Services still on `System.Diagnostics.DiagnosticSource` < 10 decoded `+` into a space, and Dapr 1.18 then rejected the next call with `invalid baggage header`.

- Downstream APM documents now show `_` in `labels.baggage_vnext_flow_version`.
- vNext's own span tag `vnext.flow.version` keeps the raw SemVer.
- Nothing in vNext reads the value back from baggage.

→ [Observability](/docs/how-to/observability)

## Fixes

### Parallel same-domain reads no longer share a `DbContext` (#1166, #1161)

Same-order (parallel) onEntry/onExit tasks run as separate branches, each in its own DI scope. A DI scope did not isolate the `DbContext`, though: the context is keyed by the ambient unit of work and the schema. Two or more in-process reads of the **same flow** in one group (`GetInstances`, `GetInstance`, `GetInstanceData`, DirectTrigger's key lookup) shared one context. The second query failed with `A second operation was started on this context instance`.

- **Before:** the failing group stopped the hook and cancelled its siblings. Without an error boundary, the instance still took its automatic transition. In the observed case it reached `success-end` with an empty result. A DirectTrigger by key faulted the instance instead.
- **Now:** each local read runs in its own non-transactional unit of work. What a read sees is unchanged, since the reads are no-tracking and see the same committed rows. Each read now costs one extra `DbContext`.

HTTP tasks were never affected, and write-side trigger tasks (Start, DirectTrigger, SubProcess) were already isolated.

→ Regression lab: [`TriggerFamilyParallelTests`](https://github.com/burgan-tech/vnext-example/pull/50) (vnext-example)

## Configuration Updates

Configuration for v0.0.103:

```json
{
  "runtimeVersion": "0.0.103",
  "schemaVersion": "0.0.59"
}
```

> **Note:** Schema **0.0.59** is required for the new PythonTask config (`handler`). Schemas 0.0.55–0.0.58 have no type `23` in the task enum.

**New settings:**

| Section | Keys (defaults) |
|---|---|
| `Workflow:PythonRuntime` (Orchestration) | `AppId` (empty = no runtime, Python tasks fail with 503; set by the Helm chart), `InvokeMethod` (`v1/invoke`), `TimeoutGraceSeconds` (5, range 1–30) |
| Python runtime container | `VNEXT_PYTHON_PORT` (8080), `VNEXT_PYTHON_HANDLERS` (`handlers`), `VNEXT_PYTHON_MAX_WORKERS` (4), `VNEXT_PYTHON_MAX_REQUEST_BYTES` / `VNEXT_PYTHON_MAX_OUTPUT_BYTES` (4 MiB) |
| Helm (chart 1.0.127) | `pythonRuntime.*` — off by default |

**Removed settings:** the Execution host's `Python:*` section (`Python:Enabled`, `Python:DefaultMode`, `Python:EnabledModes`, `Python:MaxTimeoutSeconds`, `Python:PythonNet:*`, `Python:Process:*`, `Python:Container:*`, …). The `Python:MaxTimeoutSeconds` layer is no longer part of the startup-validated timeout hierarchy.

**Database migrations:** none.

**Rollout:**
- **Domains with Python tasks:** build the domain runtime image, enable `pythonRuntime`, and republish every type-23 task with `config.handler` **before** upgrading. Steps: [v0.0.103 breaking changes](/blog/breaking-changes/breaking-changes-v0-0-103).
- **Keep the transition job budget above the longest Python wait.** That wait is `timeoutSeconds + TimeoutGraceSeconds`, at most 80 s, and it is not validated against `WorkflowExecution:TransitionJobTimeoutSeconds` (default 300).

**Container images:** published at tag `0.0.103` under `ghcr.io/burgan-tech/vnext/*`, including the new `python-runtime` base image. They are Cosign-signed (keyless OIDC) with SBOM + provenance. Immutable digests are listed in the [v0.0.103 GitHub release](https://github.com/burgan-tech/vnext/releases/tag/v0.0.103).

## Summary

- **Python Task** ⚠️: a `handler` in the domain's own runtime image, called over Dapr. `script` / `executionMode` and the Execution `Python:*` settings are removed.
- **Fix:** parallel same-domain instance reads no longer fail, and no longer turn into a silent "not found".
- **Performance:** one shared EF Core model, and fewer round-trips on nested SubFlow start chains and completions.
- **Observability:** `workflow_longpoll_resume_total` and log 20308 tell ack and fallback resumes apart. `vnext.flow.version` baggage is propagation-safe.
- **Schema** moves to **0.0.59**.
