## Overview

This release makes **`authorize` the single authorization decision point**: `GET .../instances/{id}/functions/authorize` gains an `ack=true` selector, answers `queryRoles` as a **conjunction down the whole active subflow chain**, and the in-process `queryRoles` gates on the read surfaces and the long-poll acknowledge endpoint are **removed** — an Internal Gateway that consults `authorize` before forwarding is now the boundary ([#1027](https://github.com/burgan-tech/vnext/pull/1027)). **Subflow overrides grow** so a parent can retune a child state's long-poll window and roles and swap the view a child's own rules selected, per state and per transition, while the legacy `overrides.views` / `viewOverrides` map is deprecated ([#1028](https://github.com/burgan-tech/vnext/pull/1028)). The state body now carries the **armed workflow timeout** as a `timeout` block — and in fixing that, `subFlow.overrides.timeout`, which was never actually honoured, starts firing ([#1021](https://github.com/burgan-tech/vnext/pull/1021)); `kind: "scheduled"` entries and the timeout block both carry **`annotations`** ([#1029](https://github.com/burgan-tech/vnext/pull/1029)). And the **discovery endpoint cache is invalidated by event, not by clock**: a new `POST definitions/publish/completed` is the deployment-time hook, `GET definitions/re-initialize` is removed, and the L2 TTL and periodic refresh default to `0` ([#1022](https://github.com/burgan-tech/vnext/pull/1022)). This release runs on component **schema 0.0.54**.

## Features

### `authorize` becomes the single decision point (#1027)

The deployment target is an **Internal Gateway** that introspects the caller and consults the runtime's own `authorize` function before forwarding. Enforcing `queryRoles` a second time inside the runtime was a second decision point on the same question, and two decision points drift — this repository had already paid for that twice, once when `authorize` and the state function gave opposite verdicts about the same leaf, and once when a parent's narrowing silently stopped applying. One question, one answer, one place.

**The endpoint.** `GET /api/v1/{domain}/workflows/{workflow}/instances/{instance}/functions/authorize` — an oracle, not a guard: it answers questions about a caller and admits nothing itself.

| Parameter | Required | Meaning |
|---|---|---|
| `transitionKey` | one of four | May this transition be triggered? Offered in the **current state** AND `transition.roles` AND the matching `availableIn` entry's roles |
| `functionKey` | one of four | May this **custom** function be invoked? A function with no `roles` is allowed |
| `queryRoles=true` | one of four | May this instance be read? |
| `ack=true` | one of four | **New.** May `POST .../longpoll/ack` be called? Answered through the same `ILongPollInteractionGate` the endpoint used to call — `rule` arm, else `roles`, else allow |
| `role` | no | A single role to probe — see the provider note below |
| `version` | no | Pins the workflow definition version; omitted means the instance's own |

**Exactly one** of the four selectors must be present; zero or two is a request error (`AuthorizeRequiresExactlyOneTarget`), never a silent default. The verdict is in the body on both statuses — `200 {"allowed": true}` or `403 {"allowed": false}` — so a consumer that only reads the `200` turns every refusal into "no answer". A role-resolution failure is a distinct 4xx/5xx error envelope, not a `false`.

**`queryRoles` is a conjunction.** The answer is the polled instance's own verdict **AND** every level beneath it, down to the deepest active leaf. It used to answer from the leaf alone, which made the oracle strictly *weaker* than the read gate it describes. Per level, the resolution order is: the parent's stamped `subflow.state_role_overrides` entry for the instance's `CurrentState` → that state's own `queryRoles` → the workflow root's. The override **replaces**, it does not merge, and it is read from the **child's stamp per hop** — never from the parent's definition at the point of descent, which is what had let a grandchild's gate never run.

**Parent-retained keys.** While a SubFlow correlation is open, `cancel`, `exit`, `updateData` and a **shared transition available in the parent's current state** are answered against the parent and do not descend — the same keys execution keeps on the parent (`HandleCancelPreflightStep` at order 5 skips over the forward at order 10).

**What was removed.** `InstanceQueryAppService.IsInstanceQueryAllowedAsync` and its nine call sites — `state`, `data`, `view`, `schema`, `master`, `tasks`, `actions`, `incidents`, `incidents/active` — and the `interaction.longPoll` gate on `POST .../longpoll/ack`. These surfaces no longer refuse in process and no longer consult the gate. **Role *resolution* is untouched**: `availableTransitions` filtering, state aliases, `x-roles` field filtering, the human-task list and `CallerScopeHash` cache keying all still evaluate the caller's roles. Visibility stayed; enforcement left.

:::warning
**Prerequisite, not a follow-up.** A runtime deployed **without** an Internal Gateway that calls `authorize` in front of it no longer refuses reads on `queryRoles` and no longer gates `POST .../longpoll/ack`. Attaching the gateway's authorize rules must precede deployment, and the gateway must be shown to *decide* — a route dump plus an observed deny — not merely to be in the path.
:::

Four defects were found and pinned on the way: the `queryRoles` gate read `EffectiveState` (a descendant's state key the parent's workflow cannot resolve, so the stamped override fell through to the root); state transitions were state-gated through `availableIn`, which they do not carry, so `approve` declared only on `review` answered *allowed* in `intake`; the `interaction` block was emitted from the state's **declaration** rather than from whether an ack is actually awaited (now `IsAwaitingLongPollAck`, `ResponseShapeVersion` v10 → v11); and the `role` query parameter could override an authority provider's empty answer — closed by a capability the provider *declares*, `ICallerRoleResolver`, rather than a provider-name check inside a surface. Every decision is audited under EventId **50030** with the instance id, which of the four questions was asked, the **resolved** role set and the verdict.

> **Reference:** PR [#1027](https://github.com/burgan-tech/vnext/pull/1027) — see also [Authorization](/docs/concepts/authorization) and [Built-in Functions](/docs/components/functions/built-in).

### Subflow overrides: long-poll window, roles and scoped views (#1028)

A parent that consumes a flow as a SubFlow (`state.subFlow.type: "S"`) could already replace a child transition's `roles`, a child state's `queryRoles` and the child's workflow `timeout`. It can now also tune, **per child state**, the acknowledge window and the interaction grants, and swap the view the child's own rules selected — per state and per transition:

```json
{
  "subFlow": {
    "type": "S",
    "overrides": {
      "states": {
        "otp-wait": {
          "interaction": {
            "longPoll": { "fallbackTimeoutSeconds": 180, "roles": [ { "role": "branch.teller", "grant": "allow" } ] }
          },
          "views": {
            "otp-view": { "key": "otp-view-branch", "domain": "core", "flow": "sys-views", "version": "1.0.0" }
          }
        }
      },
      "transitions": {
        "confirm": {
          "views": {
            "confirm-view": { "key": "confirm-view-branch", "domain": "core", "flow": "sys-views", "version": "1.0.0" }
          }
        }
      }
    }
  }
}
```

- **`interaction.longPoll` is field-level.** A field you write replaces the child's; a field you leave out keeps the child's. `fallbackTimeoutSeconds` must be **≥ 1**; `roles` replaces the child's list **as a whole**, and `roles: []` admits every caller (the validator warns, EventId 90006, publish response unchanged).
- **Never overridable:** the long-poll `rule`, `terminate`, and view rules. An override never adds a long-poll to a child state that declares none — that case is logged at resolution (EventId **20305**). If the child authorizes the interaction with a `rule`, a `roles` override is **ignored** (EventId **20306**) while a window override still applies.
- **Views are swapped after the child's rules selected one**, keyed by that view's key; a transition alias is normalised to the configured key. An unresolvable replacement serves the child's own view and logs EventId **20101**.
- **Resolution is child-side, on the child's `CurrentState`** — never `EffectiveState`. The overrides travel in the stamps `SubflowStarter` already writes (`subflow.state_role_overrides` / `subflow.transition_role_overrides`), so there is no new stamp key; they also apply when the child is addressed directly, and they reach exactly **one hop**: in P → C → G, P's overrides apply to C's states only, G reads C's. The stamp is a start-time snapshot — children already running keep the overrides they started with.
- The long-poll pipeline arm, the interaction gate (state function + `authorize?ack=true`) and the state body's `interaction.fallbackTimeoutSeconds` all read the same resolver, so the three always agree. Measured with the child declaring 600 s, a 120 s parent override fired after **120.2 s** and a 5 s override after **5.1 s**.

**Deprecated:** the legacy `overrides.views` / `viewOverrides` view-key map, which is still applied parent-side and still works, but **mixing it with the scoped view overrides on one subFlow is a validation error**. Authoring the new fields requires **schema 0.0.54** (`subFlowStateOverride` / `subFlowTransitionOverride` carry `additionalProperties: false`, so 0.0.53 rejects them in `npm run validate`).

> **Reference:** PR [#1028](https://github.com/burgan-tech/vnext/pull/1028) — see also [Subflow overrides](/docs/how-to/subflow-overrides) and [Workflow](/docs/components/workflow).

### Annotations on scheduled entries and the timeout block (#1029)

`kind: "scheduled"` entries in the state function never carried the transition's `annotations` — they were built from the `InstanceJob` row alone. They now resolve annotations from the definition via the job's source state (`null`, not a failure, when the source state or transition no longer resolves). State, shared, `cancel`, `updateData` and `exit` entries already carried them; that is now pinned by tests.

The workflow `timeout` gains an **`annotations`** field (schema 0.0.54, `workflowTimeout.annotations`), surfaced on the state body's `timeout` block:

```json
{
  "timeout": {
    "key": "abandoned",
    "target": "cancelled",
    "executeAtUtc": "2026-09-24T14:32:05Z",
    "annotations": { "ui/countdown": "visible" }
  }
}
```

A parent's `subFlow.overrides.timeout` replaces the child's timeout **as a whole, annotations included** — there is no merge; the stamp `SubflowStarter` writes carries them. Annotations are flow-version material, so they add no fingerprint member; the shape change moves `ResponseShapeVersion` **v11 → v12**.

The same PR bumps **Aether to 1.0.42**: inbox/outbox retention cleanup uses `FOR UPDATE SKIP LOCKED` and honours `CleanupInterval`.

> **Reference:** PR [#1029](https://github.com/burgan-tech/vnext/pull/1029) — see also [Built-in Functions](/docs/components/functions/built-in).

### Armed workflow timeout on the state body (#1021)

A client could not draw a countdown or say "auto-cancels at HH:MM": the instant was persisted on the `InstanceJob` row, but no read surface carried it. The state body now gains a **`timeout` block** — `{ key, target, executeAtUtc }` (DTO `InstanceTimeoutOutput`), omitted when the workflow has no armed timeout. The read adds **no query**: the block is projected from a fetch the state function already makes, strictly after the fingerprint `304` path declines. `ResponseShapeVersion` v9 → v10.

Answering that exposed a defect: **`subFlow.overrides.timeout` was write-only for the armed instant.** A child declaring `"timeout": null` under a parent override had a deadline that was scheduled and could never arrive — and worse, `CreateTransitionRecordStep` resolved `$timeout` at order 20 through a definition-level method that threw when the workflow had no timeout of its own, so an override-driven child died three steps before the timeout could apply and sat **Busy in its waiting state forever**. `key` and `target` now come from **one resolver** (`InstanceMetadataExtensions.ResolveEffectiveTimeout`, `override ?? workflow.Timeout`) that all four surfaces call: the arm, `FlowTimeoutJobHandler`, `ApplyTimeoutStateStep` and the state read. A malformed override stamp degrades and is reported (EventId 40108) instead of throwing out of the start request. No new column, no migration.

:::note
**Behaviour change, accepted by the Chair.** Children started with a `subFlow.overrides.timeout` now begin being pulled to the override's target — **including instances already alive**, whose jobs are armed. Nobody was relying on them *not* working, but nobody had observed them working either. Measured on `TimeoutLab`: the child reaches the override's target with the *parent's* audit key ~54 ms after the armed `ExecuteAt`.
:::

**Documented, not fixed:** `timer.reset` is required by the schema and read nowhere in the runtime — a workflow timeout always means "not finished within `duration`, from instance start", never "idle for `duration`".

> **Reference:** PR [#1021](https://github.com/burgan-tech/vnext/pull/1021) — see also [Workflow](/docs/components/workflow).

### Event-driven discovery invalidation and `publish/completed` (#1022)

Under `ServiceDiscovery:Provider=http`, the discovery endpoint cache introduced in v0.0.92 expired on a clock: a 1 h refresh window and a 2 h entry age. The cached datum — *where a domain answers* — changes when that domain is **deployed**, a rare and planned event, so a timer either fired when nothing had changed (24 registry reads a day to learn nothing) or fired too late: `3600 + fetch + 600` ≈ **70 minutes** during which calls to a moved domain went to an address it no longer answered on.

**The clock is gone.** Defaults become `L2TtlSeconds = 0` (entries never expire) and `RefreshIntervalSeconds = 0` (no periodic refresh; the warm-up loop fills the cluster once, logs `DiscoveryCacheWarmUpCompleted` 50043, and exits). Three things invalidate an entry instead:

| Trigger | Who calls it | Effect |
|---|---|---|
| `POST /api/v1/definitions/publish/completed` | the domain's CD pipeline, **once per deployment**, after the last `publish` of the package | forced full re-read of the registry |
| `POST /api/v1/utilities/discovery/refresh` | an operator | the same, by hand |
| a transport failure against a cached endpoint | the runtime itself (`RemoteTransportRouter`) | that one domain's entry is dropped (EventId **50044**), throttled per domain by `UnreachableEvictionCooldownSeconds` (**30 s**; `0` disables eviction) |

Only reachability failures evict — `ConnectionError`, `NameResolutionError`, `ConnectionRefused`, `HostNotFound`, `TimedOut` — never an HTTP error status, a TLS failure or a broken circuit: an error *response* means a domain at the right address. The residual staleness is `L1TtlSeconds` (**60 s**): every invalidation writes the shared L2, and each pod's in-process copy expires within that.

```json
POST /api/v1/definitions/publish/completed
{ "packageName": "@burgan-tech/vnext-onboarding", "version": "1.2.2", "domain": "onboarding" }
```

```json
{ "success": true, "hooks": [ { "name": "discovery-cache", "outcome": "Refreshed", "message": null } ] }
```

- The status code is **always 200** — a failed hook is reported in the body (`success: false`), because by then the components are already published and a 500 would read as a failed deployment. Gate on `success`. Idempotent: two overlapping calls produce one registry read.
- `discovery-cache` outcomes: `Refreshed`, `SkippedNotOwner` (another replica is reading — a success), `Disabled` (`ServiceDiscovery:Enabled=false`, `Provider=dapr`, or `Cache:Enabled=false`), `Failed` (retry — nothing else will). All request body fields are optional; `domain`, when supplied, is checked against the runtime's own so a pipeline pointed at the wrong runtime fails loudly.
- It runs an ordered `IPublishCompletedHook` pipeline: every hook runs even after an earlier one fails, ordered by `Order` then `Name`. New deployment-time work is a new hook, not a branch in the controller. Logged under EventIds **90001–90005**; the absence of `90001 PublishCompletedReceived` after a deployment *is* the failure mode.
- **`GET /api/v1/definitions/re-initialize` is removed** — not deprecated. It had been reduced to a no-op, and both its callers (the init host's package job and the `wf` CLI's `sync` / `update` / `reset`) made exactly this one call at exactly this moment. Both now call `publish/completed` unconditionally; the init host records the outcome as `results.publishCompleted` and a failure sets the job's own `success` to `false`. The `wf` CLI prints the per-hook outcomes; against an older runtime the 404 is a **warning only** — the exit code does not change — so a domain that keeps an old `wf` gets no invalidation and, with no TTL, no recovery until its pod restarts. **Upgrade `wf` to 1.0.14 or later before or with this runtime.**

Measured on a two-domain local run: a cached hit on `Discovery.Resolve/partner` took **1.1 ms** (`vnext.discovery.resolution=cache`, `age_seconds` 49); the live re-resolution after an eviction **39.9 ms**. Entries that never expire also mean cross-domain traffic survives a registry outage of any length.

**Rollback levers:** `RefreshIntervalSeconds=3600` + `L2TtlSeconds=7200` restores the periodic window exactly as it was, with the event-driven triggers still working on top; the validator **rejects** an expiry with no periodic refresh behind it (`L2Ttl > 0` while `RefreshInterval = 0`). `Cache:Enabled=false` restores the pre-cache path literally.

> **Reference:** PR [#1022](https://github.com/burgan-tech/vnext/pull/1022) — see also [Service discovery configuration](/docs/configuration/service-discovery) and [Workflow CLI](/docs/tools/workflow-cli).

## Behavior Changes

Three items change the runtime's boundary rather than its shape. The in-process `queryRoles` checks on `state`, `data`, `view`, `schema`, `master`, `tasks`, `actions`, `incidents`, `incidents/active` and the long-poll `ack` are **removed**, so a deployment without an Internal Gateway calling `authorize` no longer enforces them ([#1027](https://github.com/burgan-tech/vnext/pull/1027)). `GET definitions/re-initialize` returns **404**, and the discovery cache no longer expires or refreshes on a clock — a CD pipeline or `wf` CLI (≥ 1.0.14) must call `POST definitions/publish/completed` ([#1022](https://github.com/burgan-tech/vnext/pull/1022)). And `subFlow.overrides.timeout` is honoured for the first time, so running children started with one may now time out ([#1021](https://github.com/burgan-tech/vnext/pull/1021)). Two definitions that used to publish are rejected: a state-level `subFlow.type: "P"` ([#1026](https://github.com/burgan-tech/vnext/pull/1026)) and a multi-task function whose task keys normalise to the same variable name ([#1025](https://github.com/burgan-tech/vnext/pull/1025)); mixing `overrides.views` / `viewOverrides` with the new scoped view overrides is a validation error ([#1028](https://github.com/burgan-tech/vnext/pull/1028)). `ResponseShapeVersion` advances **v9 → v12** across this release, invalidating every outstanding state ETag once. Each item, its impact direction and the migration steps are documented in the [v0.0.95 breaking changes announcement](/blog/breaking-changes/breaking-changes-v0-0-95).

## Fixes

- **Multi-task functions no longer collide in `TaskResponse`** — each task's slot in `ScriptContext.TaskResponse` / `OutputResponse` now owns an isolated deep copy, so the last task's payload no longer overwrites the others; task keys that normalise to the same variable name (`user-info` and `user_info` both become `userInfo`) are rejected at publish by `FunctionComponentValidator` ([#1025](https://github.com/burgan-tech/vnext/pull/1025)).
- **A failed subflow start no longer strands the parent Busy** — a post-commit `StartSubflowJob` failure used to leave the parent Busy with no fault, no incident and no retry. It now faults with an incident, and `retry` probes the child *before* unfaulting and re-runs the missing start for the same correlation instead of unfaulting into a dead correlation. A state-level `subFlow.type: "P"` is rejected at publish with **400** — a state starts a SubFlow only; a SubProcess is started by `SubProcessTask`. EventIds 10175, 20054–20058 ([#1026](https://github.com/burgan-tech/vnext/pull/1026)).
- **Six EventId collisions in the 10xxx band resolved** — the local-task-invocation messages that landed in v0.0.94 shared `10160`–`10165` with notification and job-arming events; they move to **`10169`–`10174`**. Queries against the old ids for the notification events are unaffected ([#1024](https://github.com/burgan-tech/vnext/pull/1024)).
- **The long-poll ack fallback job row now persists `ExecuteAt`** — the same instant the Dapr job is armed with; before this it was always NULL ([#1028](https://github.com/burgan-tech/vnext/pull/1028)).
- **A malformed `subflow.timeout_override` no longer throws out of the start request** — the deserialize sat outside the method's `try` ([#1021](https://github.com/burgan-tech/vnext/pull/1021)).
- **Aether 1.0.42** — inbox cleanup now runs **at most hourly** (the configured `CleanupInterval` was previously ignored and cleanup ran every poll cycle), and outbox cleanup batches at **1000** rows; both worker `appsettings.json` files state `CleanupInterval` / `CleanupBatchSize` explicitly ([#1029](https://github.com/burgan-tech/vnext/pull/1029)).

## Configuration Updates

Configuration for v0.0.95:

```json
{
  "runtimeVersion": "0.0.95",
  "schemaVersion": "0.0.54"
}
```

> **Note:** Schema version moves to **0.0.54** — `npm i @burgan-tech/vnext-schema@0.0.54`. The schema adds `subFlowStateOverride.interaction.longPoll` / `.views` and `subFlowTransitionOverride.views` (#1028), `workflowTimeout.annotations` (#1029), `interaction.longPoll.rule` as the alternative to `roles`, the `x-indexed` validation rules with free-text `attributes.type`, and a nullable `availableIn`. The task `type` enum is unchanged.

New and changed settings:

- **`ServiceDiscovery:Cache:*`** (only under `Provider=http`) — `RefreshIntervalSeconds` default **3600 → 0** and `L2TtlSeconds` default **7200 → 0** (no periodic refresh, no expiry); new **`UnreachableEvictionCooldownSeconds`** (**30**; `0` disables failure-driven eviction). `L1TtlSeconds` returns to **60** (it was raised to 600 in v0.0.94 to stay under the hour-long window; with no window, a longer L1 only delays propagation), `TickIntervalSeconds` 60, `WarmupLockLeaseSeconds` 30, `DomainListEndpointTemplate` `/{0}/functions/domain-list`, `DomainListExpectedMax` 500. The validator rejects `L2TtlSeconds > 0` with `RefreshIntervalSeconds = 0` in every mode; the window invariants (`L1Ttl >= RefreshInterval`, `TickInterval > RefreshInterval`, …) apply only in periodic mode.
- **`Workflow:Authorization:EnforceInProcess`** — shipped briefly on the branch and **removed before release**; there is no switch. The in-process gates are gone outright.
- **CD pipelines and `wf` CLI** — call `POST /api/v1/definitions/publish/completed` once after the last `publish`; `wf` **1.0.14** does so from `sync` / `update` / `reset`.

**Response shape and ETags.** `ResponseShapeVersion` moves **v9 → v12** in this release (v10 timeout block, v11 `interaction` emitted only while `IsAwaitingLongPollAck`, v12 annotations), so every outstanding state ETag is invalidated exactly once — bounded at one full state build per (instance × callerHash) per generation per TTL. **Do not mitigate by setting `StateFunctionCache:Enabled=false`**: the `304` fast path lives inside that switch, so disabling the cache makes the warm-up spike permanent.

**Migrations.** None — the timeout override lives on the instance's `ExtraProperties`, and the subflow overrides travel in existing stamp keys.

**Container images:** published at tag `0.0.95` under `ghcr.io/burgan-tech/vnext/*`, Cosign-signed (keyless OIDC) with SBOM + provenance. Immutable digests are listed in the [GitHub release](https://github.com/burgan-tech/vnext/releases/tag/v0.0.95).

## Summary

- **`authorize` is the single decision point**: four selectors (`transitionKey`, `functionKey`, `queryRoles=true`, new **`ack=true`**), exactly one per call; `queryRoles` answered as a **conjunction** down the active subflow chain with per-hop stamped overrides; `cancel` / `exit` / `updateData` / in-state shared transitions answered against the parent. In-process `queryRoles` gates on nine read surfaces and the long-poll ack are **removed** — an Internal Gateway calling `authorize` is the prerequisite.
- **Subflow overrides** gain `states.<s>.interaction.longPoll.{fallbackTimeoutSeconds ≥ 1, roles}` (field-level; `rule` and `terminate` never overridable) and `states.<s>.views` / `transitions.<t>.views` (swap after the child's rules, child-side, one hop). `overrides.views` / `viewOverrides` are **deprecated**; mixing is a validation error.
- **State body gains `timeout`** `{ key, target, executeAtUtc, annotations }`; `kind: "scheduled"` entries carry `annotations`; `subFlow.overrides.timeout` is now **honoured**, including on already-running children.
- **Discovery cache is event-driven**: `POST definitions/publish/completed` (CD / `wf` ≥ 1.0.14), `POST utilities/discovery/refresh`, or a transport failure (30 s per-domain cooldown); `L2TtlSeconds` and `RefreshIntervalSeconds` default to **0**; `GET definitions/re-initialize` is **removed**.
- **Publish-time rejections**: state-level `subFlow.type: "P"` (400) and duplicate normalised task keys in a multi-task function; `TaskResponse` slots are isolated.
- **Fixes**: failed subflow start faults with an incident and is retryable; EventIds `10160`–`10165` → `10169`–`10174`; ack fallback job persists `ExecuteAt`; Aether **1.0.42** (hourly inbox cleanup, outbox cleanup batch 1000).
- **Response shape v9 → v12** — every state ETag invalidated once; keep `StateFunctionCache` enabled.
- **Schema** moves to **0.0.54**.
