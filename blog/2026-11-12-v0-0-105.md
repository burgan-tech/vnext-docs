## Overview

**v0.0.105** brings rule-based schema selection to transitions, caller roles to scripts, and two authorization additions. It has **one breaking change** and one database migration.

- **Rule-based transition schemas** (`schemas`): a transition picks its request schema by rule, the same way `views` picks a view ([#1225](https://github.com/burgan-tech/vnext/pull/1225)).
- ⚠️ **Function `inputSchema` with no matching entry now rejects** the request with `400 Function:800006` instead of skipping validation ([#1225](https://github.com/burgan-tech/vnext/pull/1225)).
- **Caller roles in scripts** (`context.Caller`): selection rules, automatic-transition rules, timer scripts and SubFlow output mappings can read the caller's resolved role set ([#1299](https://github.com/burgan-tech/vnext/pull/1299)).
- **May this caller start an instance?** A workflow-scoped `authorize?type=instance` route lets the gateway enforce `startTransition.roles` ([#1211](https://github.com/burgan-tech/vnext/pull/1211), [#1203](https://github.com/burgan-tech/vnext/issues/1203)).
- **`$Everyone`**: a predefined role that matches every caller ([#1196](https://github.com/burgan-tech/vnext/pull/1196), [#1193](https://github.com/burgan-tech/vnext/issues/1193)).
- **Fixes**: the data function's ETag covers the state ([#1188](https://github.com/burgan-tech/vnext/pull/1188)); an artifact-version reference prefers package-stamped rows ([#1175](https://github.com/burgan-tech/vnext/pull/1175), [#1164](https://github.com/burgan-tech/vnext/issues/1164)); concurrent `updateData` on a parked Busy instance continues the chain once ([#1195](https://github.com/burgan-tech/vnext/pull/1195)).
- **Performance**: less work per request on read, task and authorization hot paths ([#1195](https://github.com/burgan-tech/vnext/pull/1195)).

Component **schema 0.0.60** ships with this release. It adds `transitions[].schemas` and the `$Everyone` role.

## Features

### Rule-based transition schemas (#1225)

Every transition kind (state-level, shared, `startTransition`, `cancel`, `updateData`, `exit`) can declare `schemas` next to the unchanged `schema`. The shape is the one function `inputSchema` already uses:

```json
"schemas": [
  {
    "rule": { "location": "./src/IsCorporate.csx", "code": "<base64>", "encoding": "B64" },
    "schema": { "key": "corporate-payload", "domain": "core", "flow": "sys-schemas", "version": "1.0.0" }
  },
  {
    "schema": { "key": "retail-payload", "domain": "core", "flow": "sys-schemas", "version": "1.0.0" }
  }
]
```

| Situation | Result |
|---|---|
| An entry's `rule` matches | That entry's schema validates the request (first match wins, in declaration order) |
| `schemas` declared, no entry matches | `400 Transition:100025`; the instance keeps its state and is not faulted |
| No `schema` / `schemas` declared | The request is accepted |

- A rule-less entry is the fallback and must be last. `schemas` wins over `schema`. Automatic and scheduled transitions may not declare `schemas`.
- The rule is an `IConditionMapping` script. Its context carries the workflow, instance, runtime, transition, `body` (the instance's latest data, `{}` when none) and request headers — no query parameters.
- Schema selection runs before the state-machine check, so a request in the wrong state with no matching entry gets `400 Transition:100025` first.
- The instance schema function serves the rule-selected entry and answers `404` when none matches. `hasSchema` is declared-only, like `hasView`. Its cache key and ETag include a hash of the request headers (conditional and trace headers excluded), so a header-driven rule never serves another caller's entry or a false `304`.

→ [Workflow](/docs/components/workflow) · [View Selection](/docs/how-to/view-selection) · Lab: [`rule-schema-lab`](https://github.com/burgan-tech/vnext-example/pull/61) (vnext-example)

### Function `inputSchema` with no match now rejects ⚠️ (#1225)

A function whose rule-based `inputSchema` entries all carry a rule, and none of them match, now rejects a request that has a body with **`400 Function:800006`**. It used to skip validation, which left a fail-open path. To keep accepting unmatched callers, end the list with a rule-less entry.

→ [Custom Functions](/docs/components/functions/custom) · Migration: [v0.0.105 breaking changes](/blog/breaking-changes/breaking-changes-v0-0-105)

### Caller roles in scripts: `context.Caller` (#1299)

Scripts can read the caller's role set as the runtime resolved it, under either role provider (`default`: token claims, else the gateway `role` header; `morph-idm`: the identity service):

```csharp
public class IsApprover : ScriptBase, IConditionMapping
{
    public async Task<bool> Handler(ScriptContext context) =>
        await context.Caller.HasRoleAsync("morph-idm.approver");
}
```

`ScriptContext.Caller` offers `HasRoleAsync`, `RolesAsync`, `IsAvailable`, `ResolutionFailed` and `RolesFromHeader`. Roles are resolved lazily, at most once per request; a rule that never reads them makes no provider call.

| Surface | Whose roles | Provider failure |
|---|---|---|
| Selection rules (transition `schemas`, function `inputSchema`/`outputSchema`/`inputView`/`outputView`, state/transition `views`) | the request's caller | selection fails: `503 Authorization:110006` |
| Automatic-transition rule | the caller who drove the hop; none on System hops | the step fails (`110006`); the default auto transition is not taken |
| Timer script | the caller who entered the state (computed at arming); none when a fired timer re-arms | the step fails (`110006`) |
| SubFlow output mapping | the child settler's carried identity | the completion is redelivered; the parent is not faulted |
| Task mappings, transition mapping, extensions, resource lock, event mappings | unavailable | — |

- Where there is no caller, `IsAvailable` is `false` — never an empty set — and a read throws. Guard timer and automatic-rule scripts with it.
- Fail closed: when a rule read roles and the provider could not answer, the selection fails with `503` instead of falling through to a looser fallback entry.
- **Selection by role is not authorization.** Role decisions still belong to `roles` / `authorize`. Under both providers a client-supplied `role` header is taken at face value, so the gateway must strip or overwrite it.

→ [Mappings § ScriptContext](/docs/components/mappings) · Lab: [`caller-roles`](https://github.com/burgan-tech/vnext-example/pull/62) (vnext-example)

### Workflow-scoped `authorize?type=instance` (#1211, #1203)

`authorize` existed only on the instance route, so the gateway could not gate `POST .../instances/start`, and `startTransition.roles` was applied nowhere. A new route answers before any instance exists:

```
GET /api/v1/{domain}/workflows/{workflow}/functions/authorize?type=instance[&version=x][&role=r]
```

- `type` is required and ordinal; `instance` is the only supported value today. A missing or unknown value is `400 Authorization:110005`.
- `200 {"allowed": true}` / `403 {"allowed": false}`; an unknown workflow or version is `404`. Caller roles resolve exactly as on the instance route.
- Static roles and `$Everyone` compare as usual. **Instance-bound grants** (`$InstanceStarter`, `$PreviousUser`, the behalf-of roles, `$user.` / `$userBehalfOf.` / `$role.` references) never match before a start: they neither admit nor refuse. A start transition guarded only by `allow $InstanceStarter` is closed to everyone. No grants means allowed.
- The runtime itself still does not check `startTransition.roles` at `POST .../instances/start`; the gateway decides, as for every other transition. Add a second check-authorize rule for the start route and forward the start request's `version`:

```
Utils.CallApiGet("http://<orchestrator-host>/api/v1/"+path.var1+"/workflows/"+path.var2+"/functions/authorize?type=instance", header, allHeader).IsSuccessStatusCode == true
```

→ [Authorization](/docs/concepts/authorization) · Lab: [`role-matrix-lab`](https://github.com/burgan-tech/vnext-example/pull/60) (vnext-example)

### `$Everyone` predefined role (#1196, #1193)

`$Everyone` matches **every** caller: with or without roles, with or without an instance loaded. `deny $Everyone` hides a field or blocks a transition for everybody; `allow $Everyone` admits everybody, a role-less caller included.

```json
"x-roles": [{ "role": "$Everyone", "grant": "deny" }]
```

- It works on every role-grant surface: transition roles, `queryRoles`, `availableIn` roles, function roles, subflow overrides, schema `x-roles`, and as an `allOf` / `anyOf` child.
- It replaces the old "always hide this field" workaround (`deny $InstanceStarter` + `allow $InstanceStarter`), which keeps working.
- Refused at publish in `x-masking.roles` / `x-encryption.roles` (it would exempt every caller) and in `rowSecurity.rules[].roles` (`RS-E05`).
- Matching is ordinal: `$everyone` or `$EVERYONE` is a publish error.
- A static role literally named `$Everyone` now means every caller, because the predefined match runs first.

→ [Authorization](/docs/concepts/authorization) · [Row Security](/docs/concepts/row-security) · Lab: [`role-matrix-lab`](https://github.com/burgan-tech/vnext-example/pull/56) (vnext-example)

## Fixes

### The data function's ETag covers the state (#1188)

Since v0.0.80 the `functions/data` representation ETag was built only from a data fingerprint (instance id, latest data ETag, flow version, caller scope). Neither the extension output nor the state it is derived from was part of it. After a state transition that wrote no data, the fingerprint stayed the same while the extension payload changed, so the server answered `304` and the client kept a stale extension. In one eKYC flow, the client re-sent a cached `nextTransition` and got `403`.

The ETag now includes the instance's effective state, so a state change invalidates it. A `304` is still returned when nothing changed.

→ [Built-in Functions](/docs/components/functions/built-in)

### Artifact-version references prefer package rows (#1175, #1164)

An artifact-version reference (for example `"1.0.0"`) now resolves to the highest package-stamped row (`1.0.0-pkg.*`) even when a legacy bare `1.0.0` row exists. Before, the bare row shadowed every package row, and a view referenced by artifact version served a stale definition. A bare row is returned only when no package row of that artifact exists. Full-version, package-only, partial and major requests resolve as before.

### Concurrent `updateData` on a parked Busy instance continues once (#1195)

When several `updateData` requests found an instance parked in Busy (an interaction wait with no live owner), each of them took the parked pipeline over and ran the automatic chain again. That caused duplicate parent notifications and finalize calls, and a late copy wrote a stale `Status=B` over the settled state.

The continuation now first claims the instance with one set-based UPDATE on a new nullable column, `Instances.ContinuationClaimedAt` (`Status='B'`, same `CurrentState`, no claim younger than 60 s). The winner runs the chain and clears the claim. A loser drops its continuation and logs `10182` (`UpdateDataContinuationClaimLost`). The claim does not move `modifiedAt`.

→ [Transition Pipeline](/docs/concepts/transition-pipeline)

## Performance

### Less work per request on hot paths (#1195)

Behaviour-preserving changes, each pinned against the old code:

- **Representation ETag:** one pass over pooled UTF-8 (~95% less allocation). This also fixes two parser bugs: the character after `\\`, `\"` or `\/` was dropped, and a top-level array never parsed.
- **`JsonData.NormalizeJson`:** one writer pass; the output (which feeds the persisted `DataHash`) is byte-identical.
- **Tasks:** local invokers get the typed binding with no JSON round trip; no journal serialization under `history: none`.
- **Reads:** read-only instance load 3 → 2 queries; state-function cache miss 6+R → 4+R.
- **Role grants:** the dynamic-grant context is built once per evaluator instead of copying all instance data per transition.

Hosts also name their Postgres connections: when a connection string has no `Application Name`, it is set from `OTEL_SERVICE_NAME`, else `DAPR_APP_ID`, else the host name. `pg_stat_activity` and PgBouncer `SHOW CLIENTS` then show the owning host. Nothing else in the connection string changes; pool sizing stays with PgBouncer.

## Upgrade Notes

- **Run DbMigrator before the hosts.** Migration `20261109120000_AddInstanceContinuationClaim` adds the nullable `Instances.ContinuationClaimedAt` column.
- **Function `inputSchema`:** a rule-based list with no rule-less last entry now rejects unmatched requests. See [v0.0.105 breaking changes](/blog/breaking-changes/breaking-changes-v0-0-105).
- **One-time ETag change:** a body containing an escaped backslash, quote or slash gets a new representation ETag. Such clients see one `200` instead of a `304`, also between old and new pods during a rolling deploy.
- **Log level:** the per-task "Executing task … with error-aware retry" and "Task … completed successfully" lines move from Information to Debug.
- **Gateway:** add the `authorize?type=instance` rule for the start route if you want `startTransition.roles` enforced, and make sure the gateway strips or overwrites a client-supplied `role` header.

## Summary

- **Transitions** select their schema by rule (`schemas`); no match is `400 Transition:100025`.
- **Function `inputSchema`** ⚠️: no match now rejects with `400 Function:800006`.
- **Scripts** read caller roles through `context.Caller`; a provider outage fails closed with `503 Authorization:110006`.
- **Authorization:** `authorize?type=instance` gates instance start; `$Everyone` matches every caller.
- **Fixes:** data-function ETag covers the state; artifact versions prefer package rows; parked Busy continuations are claimed once.
- **Schema** moves to **0.0.60**. Run DbMigrator first.
