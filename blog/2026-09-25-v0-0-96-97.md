## Overview

This post consolidates two interim versions — **v0.0.96 and v0.0.97** — shipped one day apart on September 24 and 25, both confined to **caller role resolution**. **v0.0.96** makes the `morph-idm` caller-role provider **fail open to an empty role set**: an error status, a timeout, a transport error, an unparseable body and a `204` all resolve to `[]` instead of `403 Authorization:110004`, and a caller with neither `act_sub` nor `client_id` is not sent to the identity service at all. That is only safe because of a new **canonical rule 5** shipped with it: **a caller with no roles cannot clear a role-bound deny**, on every surface and under every provider — so an outage can narrow what a caller sees but can never widen it ([#1032](https://github.com/burgan-tech/vnext/pull/1032)). **v0.0.97** then makes a request's **`role` header decisive under `morph-idm`**: a non-blank header replaces the identity service's answer and morph-idm is not called, and `authorize`'s `?role=` parameter behaves like that header when the request carries none — expressed as a mode the provider declares, `ICallerRoleResolver.RoleParameterMode` ([#1034](https://github.com/burgan-tech/vnext/pull/1034)). Both releases run on component **schema 0.0.54**, unchanged from v0.0.95.

## Features

### Fail-open role resolution, closed role-bound denies (#1032)

*Shipped in v0.0.96.*

Under `CallerRoleProvider:Provider=morph-idm`, every failure to fetch the caller's operation set — a 5xx, a timeout, a DNS or TLS error, a body with no recognizable roles array — answered **403 `Authorization:110004`** (`CallerRoleResolutionFailed`) on every surface, on the reading that an unknown role set must deny. An identity-service outage therefore broke every read, not just the ones that depended on a role.

**The resolver no longer fails.** For a request without a `role` header, each case resolves to an **empty role set** and the request is evaluated on it:

| Case | Log | `vnext.auth.outcome` | Tag that tells it apart |
|---|---|---|---|
| neither `act_sub` nor `client_id` (anonymous / device token) — **no call is made** | Debug **20464** | `skipped` | — |
| `204`, blank body, `roles: []` | Warning 20441 | `empty` | `vnext.auth.empty_reason` = `no_content` / `empty_body` / `empty_array` |
| non-success status | Error 20442 | `failed` (span Error) | `vnext.auth.failure_kind` = `http_status` + `vnext.auth.provider.status_code` |
| HttpClient timeout | Error 20442 | `failed` | `failure_kind` = `timeout` |
| connection / DNS / TLS | Error 20442 | `failed` | `failure_kind` = `transport` |
| success status, no recognizable roles array | Error **20463** | `failed` | `failure_kind` = `parse` |

The outcome is memoized for the scope, and every memo-hit span repeats its tags. `Authorization:110004` is no longer produced by either built-in provider; the code is kept for a future provider that needs the failure channel.

**Why an empty set is safe: canonical rule 5.** An empty role set already denies what matters — an allowlist grant cannot match it. What it did *not* do, until now, was refuse a **blacklist**: a grant set with only deny grants is "allowed unless explicitly denied", and with no roles to compare, "nothing matched" read as a pass. Every deny-only guard was a blanket allow for an anonymous token, a device token, a token minted by a process that carries no roles — and, under `morph-idm`, for any caller during an outage. The grant author wrote a refusal and the runtime waived it.

> **Rule 5.** A caller with no roles cannot clear a **role-bound** deny. A static role (`blocked`) or a `$role.$.context…` reference is a statement about the caller's *roles*; with none to compare, the deny refuses. **Identity-bound** denies — the four predefined roles and `$user.` / `$userBehalfOf.` — match on the caller's identity, not its roles, and keep their normal evaluation.

| Grant set | Caller roles | Result |
|---|---|---|
| `[deny: blocked]` | `[teller]` | allowed (blacklist) |
| `[deny: blocked]` | none | **refused** (rule 5) |
| `[deny: $InstanceStarter]` | none, caller is not the starter | allowed (identity-bound) |
| `[allow: $InstanceStarter, deny: blocked]` | none, caller is the starter | **refused** (rule 5) |
| `[allow: teller]` | none | refused (allowlist, nothing matched) |

The rule lives in the one evaluator (`TransitionAuthorizationManager.IsUnprovableRoleBoundDeny`, shared by `RoleGrantEvaluator` and `EvaluateRolesStatic`), so it applies to every provider and every surface: `availableTransitions`, `authorize`, `x-roles` field filtering, the human-task list and function `roles`. It **reverses**, for role-bound denies, the v0.0.79 change that let role-less callers see deny-only `x-roles` fields. The fail-open change and rule 5 ship together and must not be separated: without rule 5, every blacklist would have become a blanket allow during an outage.

**Also in this change:** `authorize?ack=true` now adds the `role` parameter to the caller's roles on every path — an awaiting instance without an active SubFlow used the fallback instead, so the same caller got a different role set depending on the instance's shape.

Measured live on `role-matrix-lab` (`submit-for-review` = allow maker / approver, deny viewer; `reject` = deny auditor only): empty, failed and unasked callers see neither transition and `authorize` returns `403 {"allowed":false}` for both; a caller with an unrelated role still sees `reject`; the state function returns **200** in every case.

:::note
**Reliability observation, not changed here.** The morph-idm `HttpClient`'s circuit breaker is process-wide: 20 consecutive transient failures, with 1 retry per request, open it for 30 s. Measured: 10 consecutive 500s for **one** user opened it, and for 30 s **every** caller was evaluated as role-less (`failure_kind=transport`). It fails in the safe direction, but the blast radius is wide; tracked as a separate follow-up.
:::

> **Reference:** PR [#1032](https://github.com/burgan-tech/vnext/pull/1032) — see also [Authorization](/docs/concepts/authorization).

### The `role` header and `?role=` decide under `morph-idm` (#1034)

*Shipped in v0.0.97.*

Under `morph-idm`, the request's `role` header was ignored — the identity service's answer was the only authority, and the header was never forwarded to it (forwarding would degenerate the endpoint into a yes/no check for that single role). By committee decision of 2026-09-25 the header is now **decisive**:

| Request | Role set | morph-idm called? | `vnext.auth.outcome` | Log |
|---|---|---|---|---|
| carries a non-blank `role` header | the header's roles — **replaces** the service's answer, no merge | **no** | `header` | Debug **20465** |
| carries no `role` header (or only a blank one) | the service's operation set — or `[]` on any failure (v0.0.96) | yes | `resolved` / `empty` / `failed` / `skipped` | see above |

"The `role` header" is read exactly as the default provider reads it: `ICurrentUser.Roles`, which the framework parses from the header, else the forwarded header dictionary in a scope with no HTTP request. The `role` header is still never sent to morph-idm. The decision is memoized for the scope.

**`authorize`'s `role` query parameter behaves like the header.** Once the header became decisive, keeping the parameter ignored made the same claim answer `200` through the header and `403` through the query string. How the parameter composes is now stated by the provider through **`ICallerRoleResolver.RoleParameterMode`**, which replaces the `AllowsRoleParameterFallback` bool introduced in v0.0.95:

| Provider (mode) | `transitionKey`, `functionKey`, `queryRoles` | `ack` |
|---|---|---|
| `default` (`Fallback`) | **fallback** — used only when the provider resolved no roles; a `role` header therefore wins | **additive** — merged with the provider's roles, on every path |
| `morph-idm` (`AsRoleHeader`) | **as the `role` header** — when the request has no header of its own, `?role=X` is handed to the resolver as that header: the role set is `[X]` and morph-idm is not asked; a real header wins | same as the other targets |

Measured on `role-matrix-lab` (`submit-for-review` = allow maker, allow approver, deny viewer):

| Request | `default` | `morph-idm` |
|---|---|---|
| no header, no parameter | 403 | 403 (morph-idm's answer) |
| no header, `?role=maker` | 200 | 200 — morph-idm not asked |
| header `role: maker` | 200 | 200 — morph-idm not asked |
| header `role: chain.other`, `?role=maker` | 403 — header wins | 403 — header wins |

MockLab's request log confirmed the mechanics: requests carrying the header, and `?role=` requests without one, produced **0** `get-roles` calls; parameter-less requests produced 1; no morph-idm call ever carried a `role` header. The mode lives on the resolver rather than on a provider-name check at a surface, so a new provider has to state its own answer instead of inheriting one. **The `default` provider is unchanged.**

:::warning
**More permissive by design.** A caller that sends roles in the `role` header, or in `authorize`'s `?role=`, is evaluated with exactly those roles and the identity service is bypassed. The component that sets these values — the gateway — is therefore the authority for such requests: it must strip or own the `role` header on every inbound request, or a client can assert its own roles.
:::

> **Reference:** PR [#1034](https://github.com/burgan-tech/vnext/pull/1034) — see also [Authorization](/docs/concepts/authorization) and [Built-in Functions](/docs/components/functions/built-in).

## Behavior Changes

Both versions change what a caller is authorized to see, in opposite directions. **v0.0.96** is *more restrictive*: a transition, function or `x-roles` field guarded **only** by a role-bound deny is no longer visible to anonymous, device or otherwise role-less callers (rule 5), reversing the v0.0.79 behaviour for deny-only fields; and `morph-idm` no longer answers `403 Authorization:110004` on a resolution failure — the request proceeds on an empty role set ([#1032](https://github.com/burgan-tech/vnext/pull/1032)). **v0.0.97** is *more permissive by design*: under `morph-idm` a non-blank `role` header, or `authorize`'s `?role=` without a header, replaces the identity service's answer, and the gateway becomes the authority for those values; `ICallerRoleResolver.RoleParameterMode` replaces the `AllowsRoleParameterFallback` bool for custom providers ([#1034](https://github.com/burgan-tech/vnext/pull/1034)). There are no API or contract shape changes and no migrations. Each item, its impact direction and the migration steps are documented in the [v0.0.96–97 breaking changes announcement](/blog/breaking-changes/breaking-changes-v0-0-96-97).

## Fixes

- **`authorize?ack=true` resolves the `role` parameter the same way on every path** — an awaiting instance without an active SubFlow used the fallback rule instead of the additive one, so the same caller got a different role set depending on the instance's shape ([#1032](https://github.com/burgan-tech/vnext/pull/1032)).
- **Stale comments corrected** — several still described the removed in-process `queryRoles` read gate or a fail-closed provider ([#1032](https://github.com/burgan-tech/vnext/pull/1032)).
- **Version labels corrected in `vnext-meta`** — #1032 shipped in v0.0.96, not 0.0.94/0.0.95 as its metadata first claimed; `callerRoleResolutionEmptyOnFailure` and the `roleless-caller-cannot-clear-role-bound-deny` policy are `since` / `enforcedSince` **0.0.96** ([#1034](https://github.com/burgan-tech/vnext/pull/1034)).

## Configuration Updates

Configuration for v0.0.97:

```json
{
  "runtimeVersion": "0.0.97",
  "schemaVersion": "0.0.54"
}
```

> **Note:** Schema version is unchanged at **0.0.54** across both versions.

No new settings. `CallerRoleProvider:Provider` (`default` | `morph-idm`) keeps its meaning; what changes is the behaviour under `morph-idm`. Two things to verify before upgrading a `morph-idm` deployment:

- **The gateway owns the `role` header.** From v0.0.97 a `role` header on an inbound request is the caller's role set. Confirm the gateway strips or sets it on every route.
- **Dashboards.** New Debug logs **20464** (call skipped, no identity) and **20465** (roles taken from the header), new Error **20463** (unparseable body); span tag `vnext.auth.outcome` now covers `resolved | empty | skipped | failed | header`, with `vnext.auth.failure_kind` (`http_status | timeout | transport | parse`) and `vnext.auth.empty_reason` (`no_content | empty_body | empty_array`). Alerts keyed on `Authorization:110004` will go quiet.

**Custom providers.** An `ICallerRoleResolver` implementation that overrode `AllowsRoleParameterFallback` must now return a `RoleParameterMode` (`Fallback` | `AsRoleHeader`); the interface default is `Fallback`.

**Container images:** published at tags `0.0.96` and `0.0.97` under `ghcr.io/burgan-tech/vnext/*`, Cosign-signed (keyless OIDC) with SBOM + provenance. Immutable digests are listed in each GitHub release: [v0.0.96](https://github.com/burgan-tech/vnext/releases/tag/v0.0.96), [v0.0.97](https://github.com/burgan-tech/vnext/releases/tag/v0.0.97).

## Summary

- **`morph-idm` fails open to an empty role set** (v0.0.96): error status, timeout, transport error, unparseable body and `204` all resolve to `[]`; callers with neither `act_sub` nor `client_id` are not sent to the service; `403 Authorization:110004` is no longer produced. Span tags `vnext.auth.failure_kind` / `vnext.auth.empty_reason`, logs 20463 / 20464.
- **Canonical rule 5** (v0.0.96): a role-less caller cannot clear a role-bound deny, on every surface and provider; identity-bound denies unaffected. *More restrictive* — reverses v0.0.79 for deny-only `x-roles` fields.
- **`authorize?ack=true` adds `?role` on every path** (v0.0.96).
- **`role` header decides under `morph-idm`** (v0.0.97): a non-blank header replaces the service's answer and morph-idm is not called (`vnext.auth.outcome=header`, log 20465); `?role=` behaves like the header when none is present; a real header wins. *More permissive by design* — the gateway is the authority.
- **`ICallerRoleResolver.RoleParameterMode`** (`Fallback` | `AsRoleHeader`) replaces the `AllowsRoleParameterFallback` bool (v0.0.97); `default` provider unchanged.
- **Schema** stays at **0.0.54**.
